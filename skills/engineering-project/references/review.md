# 评审

`audit.md` 讲**审什么**，这份讲**怎么审**——评审是一个有输入、有格式、有闭环的
动作，不是"看一眼点同意"。

在 AI 协作里，评审是唯一持续起作用的质量闸门。所以它必须**便宜且可重复**：
一次评审超过半小时，人就会开始跳过；跳过几次之后，整套流程就只剩形式。

---

## 一、三种场合

| 场合 | 触发 | 看什么范围 | 时间预算 | 核心问题 |
|---|---|---|---|---|
| **切片评审** | 每个 PR | 这次 diff | 15 分钟 | 这条切片做对了吗 |
| **缺陷评审** | 每次修 bug | diff + 根因 | 10 分钟 | 为什么没被测住？同类还有吗 |
| **里程碑复盘** | 一组切片完成 / 阶段结束 | **整个仓库** | 30—45 分钟 | 这套东西整体还立得住吗 |

前两种是增量的，跑 `make audit`。第三种是全量的，跑 `make review`。

---

## 二、请求评审：AI 侧的格式

不要只说"做完了，请 review"。按 `slices.md` 的五段汇报，外加三样：

```markdown
## 请求评审：REQ-ORD-003 库存不足时拒绝下单

### 变更
git diff --stat 的输出（贴出来）

### 验证
make check 的输出（贴出来，不要只说"全绿"）

### 我最不确定的三个地方          ← 这一节最重要
1. 库存扣减用了 SELECT FOR UPDATE，高并发下锁等待时间没测过
2. 429 和 409 的选择：库存不足我返回了 409，但 contracts/errors.md 里
   没有明确规定这种情况，可能和别处不一致
3. 事务边界放在了 app 层的 placeOrder，但退款路径也会碰库存，
   那条路径我没动，可能需要同样的处理
```

**"我最不确定的三个地方"是整个协议里性价比最高的一条。**
让 AI 自己指出弱点，比让人从零把整个 diff 扫一遍便宜一个数量级——
它知道自己在哪里猜了，只是默认不说。

强制要求写满三条。如果 AI 说"没有不确定的"，那它不是在找问题，
这本身就是一个该被追问的信号。

---

## 三、给反馈：三级 + 指向行为

| 级别 | 含义 | 处理 |
|---|---|---|
| **阻塞** | 不改不能合 | 必须逐条修完并说明怎么验证的 |
| **建议** | 该改，但可以现在改也可以记成任务 | 明确说是哪一种，别含糊 |
| **记录** | 不用改，但值得写进 ADR / runbook / 术语表 | 落盘，别留在评审对话里 |

`audit.md` 里的 🔴 必审项出问题，一律是阻塞。

两条硬要求：

1. **反馈指向行为，不是风格。**
   ✅「库存为 0 时这里返回 500 而不是 409，和 REQ-ORD-003 不符」
   ❌「这段写得不太好」
   前者 AI 能直接修，后者它只会把代码重新排列一遍然后说改好了。
2. **每条反馈附"怎么算修好了"。** 没有验收条件的反馈会来回三轮。

---

## 四、收到反馈：AI 侧最容易出问题的地方

按顺序：

### 1. 先复述，再动手

用自己的话说一遍"你的意思是 X 会导致 Y"，确认理解对了再改。
这一步省不掉——**修错东西的成本远高于多问一句**。

### 2. 不许表演性同意

「你说得对，我马上改」然后改掉症状——这是最坏的情况：评审者以为问题解决了，
实际上根因还在，而且现在被一层补丁盖住了，更难发现。

**反馈也可能是错的。** 如果你有具体技术依据（指向某行代码、某份文档、某条测试），
就说出来，别默认顺从。评审是双向的：

> 「这里我确认过：`contracts/errors.md` 第 12 行规定库存类冲突用 409，
> 所以 429 在这里不合适。要改的话得先改契约。」

这比顺从有价值得多。反过来，如果只是道歉然后照做，评审者应该警惕——
说明 AI 可能没理解问题。

### 3. 一次只修反馈，不夹带

修反馈的同时顺手重构别处，会让二次评审重新变贵——评审者要重新分辨
「这块变化是修反馈还是你自己加的」。想改的别的，记成新任务。

### 4. 逐条回应

每条阻塞项说清楚：改了什么、**加了哪条测试证明它修好了**。
没有测试的"修好了"不算修好。

---

## 五、闭环

- 二次评审**只看阻塞项**，不重新审整个 diff
- 二次评审应该 ≤ 5 分钟。超了说明第一次的反馈不够具体，
  下次反馈要写得更可执行
- 建议项要么当场改，要么落成任务，**不许"记住了"**——记住的东西会丢
- 记录项当场写进 `docs/decisions/` 或 `docs/glossary.md`

---

## 六、里程碑复盘

每个 PR 都过了，不代表整体还立得住。侵蚀是一点一点发生的，
只有拉远了看才看得见。

**什么时候做**：一组切片完成、一个阶段结束、或者两周一次——取早的那个。

先跑 `make review`（机器能查的它都查了），然后人看这八条：

| # | 问 | 侵蚀的样子 |
|---|---|---|
| 1 | **spec 还成立吗** | 非目标被突破了；验收标准和实际行为对不上 |
| 2 | **术语漂移了吗** | 代码里出现了术语表里没有的核心名词；同一概念有了两个名字 |
| 3 | **架构侵蚀了吗** | `domain/` 里出现了数据库/HTTP 调用；上下文之间开始直接读对方的表 |
| 4 | **测试还可信吗** | skip 数量在涨；异常路径没跟上；有为了让代码过而放宽的断言 |
| 5 | **技术债登记了吗** | 那些口头说"以后再说"的，写下来了吗 |
| 6 | **依赖膨胀了吗** | 多了几个？有没有做同一件事的两个库 |
| 7 | **文档过期了吗** | README 的命令还能跑吗；runbook 上次演练是多久前 |
| 8 | **下一阶段最大的风险是什么** | 对照 `architecture.md` 的风险表，重排一次 |

**产出**：一段复盘记录（写进 `docs/decisions/` 或单独的复盘文件）、
若干条新任务、可能一份新 ADR（如果发现某个原始决策已经不成立）。

复盘不是走过场。**至少要产出一条改动**——如果八条全是"没问题"，
通常意味着看得不够仔细，或者这段时间根本没做多少事。

---

## 七、评审的反模式

| 现象 | 为什么是问题 |
|---|---|
| PR 太大，扫一眼点同意 | 闸门形同虚设，还不如没有。见 `slices.md` 的尺寸上限 |
| 评论格式和空格 | 免审项占了必审项的时间。塞进 CI |
| 只看 AI 说改了什么，不看 diff | AI 的自述和实际改动可能不一致 |
| 信 AI 贴的测试输出 | 自己跑一次 `make check` |
| 反馈攒成一大段 | 分级、逐条、可执行 |
| 从不复盘，只做 PR 评审 | 侵蚀在每个 PR 里都合规，只有拉远了才看得见 |
| 修完反馈不做二次确认 | 「改好了」不等于改对了 |
