# 复用与借鉴

**动手写之前，先花十分钟找找有没有现成的。**

这十分钟的回报通常是几小时到几天。而 AI 在这一步的默认行为是**直接开始写**——
它写代码的成本太低，低到"先搜一下"看起来反而像绕路。

反过来也有一个坑：为了"不重复造轮子"引入一个维护很差的小包，
或者抄了一段自己看不懂的代码。所以这份文档有两半：**先找，然后适配**。
只做前一半的复用是负债。

---

## 一、检索顺序：四层，从便宜到贵

**每一层都比下一层便宜。** 按顺序问，第一层就命中的话，后面都不用问。

### 第 1 层：这个仓库里已经有了吗 ← 最常被跳过

AI 最常见的重复造轮子形式，不是引错了库，是**在仓库里已经有一个
`formatDate` 的情况下又写了一个**。它不会主动全局搜。

动手前的固定动作：

```bash
# 按名字找
grep -rn "关键词\|类似的函数名" src/ --include='*.*' | head -20
# 按用途找（相似的字符串、错误消息、注释）
grep -rni "这个功能会出现的词" src/ | head -20
# 历史里有没有做过
git log --oneline --all | grep -i "关键词"
```

同一个概念在这个仓库里已经有实现的话，**用它或者扩展它**，不要并行再写一个。
两个做同一件事的实现，一定会有一个先过期，且没人知道是哪个。

### 第 2 层：标准库 / 运行时里有吗

大量"工具函数"是在重写标准库。写之前查一下语言标准库的对应模块——
日期、路径、URL、编码、集合操作、随机数。

### 第 3 层：已经装了的依赖里有吗

先看 `package.json` / `pyproject.toml` / `Cargo.toml`。
你可能已经装了一个框架，它自带了校验、重试、日志、配置加载。
**用已有依赖 > 加新依赖**，因为新增依赖的成本不只是安装。

### 第 4 层：生态里的成熟方案

到这一步才考虑新增依赖，走 `architecture.md` 的**依赖准入检查**。

## 二、这些必须用成熟方案，不许手搓

这一节限定了 `architecture.md` 里那条"自己写 50 行能不能替代"——
**那条只对边界情况可枚举的小工具成立**。下面这些一律用成熟实现：

| 类别 | 例子 |
|---|---|
| **安全** | 密码哈希、加密、JWT/token 签发与校验、CSPRNG 随机数、CSRF/XSS 防护 |
| **协议与格式** | HTTP、TLS、JSON/YAML/CSV 解析、URL 解析、邮件地址校验 |
| **时间与时区** | 时区换算、夏令时、日期解析与格式化 |
| **文本与编码** | Unicode 规范化、大小写转换、排序、分词 |
| **数据库** | 驱动、连接池、迁移工具、查询构造 |
| **金额** | 十进制精度运算 |
| **弹性** | 重试与指数退避、限流、熔断 |

**判据：这个东西的边界情况，我能列全吗？**

列不全就用成熟的。上面这些的共同点是——**错了很贵，而且错误不会立刻显现**。
一个自己写的密码哈希、一个自己写的时区换算，在测试里全绿，
在上线三个月后才以最难堪的方式暴露。

> CSV 解析看起来是"按逗号分割"，直到你遇到引号里的逗号、
> 引号里的换行、BOM、CRLF、转义引号。这就是"边界情况列不全"的样子。

---

## 三、这些该自己写

- **业务规则**——这是你的核心，没有库能替你写。用库来实现领域逻辑通常是错的
- 只用一次的几十行胶水，且边界情况能列全
- 那个库的 API 比自己写还复杂
- 为了用 1% 的功能要引入一整个框架
- 依赖维护很差（半年没提交、issue 堆积）而功能又不难

---

## 四、借鉴结构，不只是引入依赖

**值得抄的不只是代码，更多时候是"它为什么这么分"。**

去哪看：

1. **官方的 example / starter**——框架作者示范的组织方式
2. **同类开源项目**——尤其是规模和你接近的
3. **你自己以前的项目**——最容易被忘掉的一处。你踩过的坑已经在里面了

看什么：目录怎么分层、错误怎么组织、配置怎么加载、测试怎么摆、
契约放在哪、迁移怎么管。

**抄模式，不要抄代码。** 先能说出"它为什么这么分"，再决定要不要照做。

### 抄结构的风险

**一个项目的结构承载着它的假设**：团队规模、部署形态、变更频率、
它要支持的扩展方向。

把一个为百人团队、多服务部署设计的目录结构，搬到一个单人项目上，
是净损失——你得到了它的全部成本，却用不上它解决的任何问题。

判据：**这个结构在解决什么问题？我有这个问题吗？** 没有就别抄。

## 五、个性化适配 ← 少了这一半，复用就是负债

抄进来的东西不适配，比自己写更糟：它会带进另一个项目的假设、
另一套命名、另一种错误处理方式，而且看起来像是"标准做法"，没人敢改。

四条，缺一不可：

### 1. 命名换成你的通用语言

抄来的 `User` / `Item` / `Handler` / `data`，换成 `docs/glossary.md` 里的词。

**不换的话术语表就废了**——代码里会同时存在两套词汇，
而且新来的人（和下一个会话的 AI）不知道该跟哪套。

### 2. 删掉用不到的部分

starter 模板里通常 80% 是给别人的场景准备的：多环境配置、
国际化、你不用的中间件、示例路由。

**留着的每一行都要被维护、被评审、被 AI 读进上下文。**
这直接对应 `proportion.md`：没人要的代码消耗的是同一个稀缺资源。

### 3. 让它符合本项目约定

- 错误走统一信封（`contracts/errors.md`），不要留着它自己的错误格式
- 日志走本项目的结构化格式，带 traceId
- 配置从环境变量读，不要留着它的配置文件方案
- 放进 `src/<上下文>/` 的正确位置，不要留着它的目录名
- 命令挂到标准动词上（`stack.mk`），不要在 README 里加一条特殊命令

### 4. 抄之前先看懂

**看不懂的代码不要抄进来。** 出问题时你没法调，AI 也只会在它周围
反复试探而不敢动它。

这是最实用的一条防线：如果解释不了它每一行在干什么，
要么花时间看懂，要么别用。

> **总判据：抄进来的东西，读起来应该像是这个项目里长出来的，
> 而不是贴上去的。**

## 六、AI 在这一步的典型失败

| 失败 | 怎么发现 |
|---|---|
| **不搜就写**——仓库里已经有了又写一个 | 评审时 grep 一下这个功能的关键词，看有没有两处 |
| 手搓安全/时间/解析相关的东西 | 看第二节的表，命中就是阻塞 |
| 引入整个框架只用 1% | 问：用到了它的哪几个功能 |
| **默写训练数据里的 boilerplate** | 它带着别的项目的假设：不同的错误格式、不同的命名、不同的配置方式。搜代码里有没有和本项目约定不一致的写法 |
| 抄了但没适配 | 术语没换、错误没走统一信封、目录位置不对 |
| 抄了看不懂的代码 | 问它这段在干什么，答得含糊就是没看懂 |
| 为"不造轮子"引入烂包 | 走依赖准入检查：维护状态、issue、间接依赖 |

---

## 七、把结论写进 ADR

"用 X 而不是自己写"和"自己写而不用 X"**都是决策**，都值得留痕。

尤其是后者：不写下来的话，后来者（和三个月后的 AI）会以为
这里根本没调研过，然后"顺手"给你换成一个库。

ADR 里写清楚：调研了哪些选项、为什么选这个、**做了哪些适配**。
最后这项在换版本、换库的时候是救命的。
