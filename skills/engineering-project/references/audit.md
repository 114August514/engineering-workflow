# 人该审什么

**每个闸门都读这一份。**

这份讲**审什么**。**怎么审**（请求评审的格式、反馈三级、收到反馈怎么处理、
闭环，以及里程碑复盘）在 `review.md`。修 bug 的专门流程在 `bugfix.md`。

前提认知：**人的评审精力是这套流程里最稀缺的资源。** AI 写代码的成本趋近于零，
人审代码的成本没有变。所以审计不能"全都看一遍"——那只会退化成扫一眼点同意。
必须按**可逆性 × 影响半径**分级，把精力集中在少数几个地方。

---

## 一、分级

### 🔴 必审——不可逆或有放大效应

这些东西错了，代价不是"改一下"，是"重写"或"数据没了"。**逐字看。**

| 类别 | 具体看什么 |
|---|---|
| **非目标与验收标准** | 范围有没有悄悄膨胀；标准能不能被机器判定 |
| **术语与不变量** | 有没有新造同义词；不变量有没有落到数据库约束 |
| **ADR** | 决定、后果、反悔成本；有没有"顺手"引入没被需求逼出来的复杂度 |
| **数据库 schema 与迁移** | 字段类型/可空/索引/外键；`down` 是否真能回滚；破坏性变更是否三步走 |
| **对外 API 契约** | 每个字段的必填与单位；**错误路径**；破坏性变更 |
| **认证与授权** | 谁能做什么；有没有"忘了检查"的路径；越权能不能拿到别人数据 |
| **密钥与配置边界** | 有没有硬编码；`.env` 有没有进仓库；日志里有没有敏感信息 |
| **钱 / 隐私 / 删除数据的代码路径** | 金额精度与舍入；删除是软删还是硬删；有没有二次确认 |
| **新增依赖** | 维护状态、许可证、间接依赖、能不能自己写 50 行 |
| **发布与回滚流程** | 回滚步骤是否演练过 |

### 🟡 抽审——可逆，但 AI 高频出错

不必逐行，但每个 PR 至少挑两三处看。

- **测试是不是真的在测行为**（见下面第三节，这是最重要的一项）
- **有没有过度设计**：只有一个实现的接口、没人用的配置项、为想象中的故障写的防御。
  问一句「哪条 REQ 要求了这个」「这个情况实际发生过吗」。判据见 `proportion.md`
- **有没有重复造轮子**：仓库里是不是已经有一个了（grep 一下功能关键词）；
  有没有手搓安全/时间/解析类的东西（这是阻塞项）；
  抄来的代码适配了吗——命名换成术语表的词了吗、错误走统一信封了吗。见 `reuse.md`
- 错误处理：有没有被吞掉、有没有丢失原始错误、重试会不会打爆下游
- 事务与并发边界：该在一个事务里的有没有拆开；有没有竞态
- 数据库访问：循环里查询（N+1）、缺索引的全表扫、没有分页的列表接口
- 日志：关键路径有没有日志、有没有过量日志、有没有漏敏感信息
- 前端：加载/空/错误三态是否都处理、表单是否可用键盘完成、对比度

### ⚪ 免审——机器把关，人看就是浪费时间

**这些出现在人的评审视野里，本身就是流程出了问题。**

格式、import 顺序、命名风格、行长、lint 规则、类型错误、覆盖率阈值、
依赖漏洞扫描、许可证扫描。

全部塞进 `make check` 和 CI，让它们在人看到之前就被挡掉。
人在 PR 里评论"这里少个空格"是一种浪费。

## 二、十五分钟审一个 PR

顺序很重要，**从最便宜的信号开始**，前三步就能筛掉大部分问题：

```
1. git diff --stat            —— 碰了哪些文件？有没有进禁区？有没有莫名其妙的文件？
2. 看 contracts/ 和 migrations/ 的 diff  —— 必审区，逐字看
3. 看依赖文件的 diff          —— 有没有偷偷加依赖
4. 看测试                     —— 断言了什么？有没有异常路径？（第三节）
5. 抽看核心逻辑               —— 只看这次改动的领域逻辑，不看胶水代码
6. 自己跑一次 make check      —— 不要信 AI 贴的输出
```

`make audit` 会把 1—3 步自动做完并生成清单。

**第 6 步别省。** AI 报告"测试全过"而实际没跑、或者跑的是改过的测试，
是真实发生过的失败模式。

## 三、怎么判断测试是不是真的

这是审计里性价比最高的一件事。四个动作：

1. **看断言，不看数量。** 一个测试里有几个 `assert`？断言的是返回值和状态，
   还是"某个 mock 被调用了"？
2. **把实现改坏，看测试红不红。** 最狠也最快：把一个 `>` 改成 `>=`，
   或者让函数直接 `return null`，跑测试。**没红的测试是假的。**
3. **搜异常路径。** spec 里每条"如果……那么……"，在测试里搜得到吗？
4. **看 git 历史。** 这次 PR 有没有**修改**已有测试？修改已有测试是高危信号——
   要么需求真变了（那 spec 也该变），要么是为了让新代码过而放宽了断言。

## 四、AI 典型失败模式清单

按"审的时候怎么快速发现"组织。这份清单直接当 review checklist 用。

| 失败模式 | 长什么样 | 怎么快速发现 |
|---|---|---|
| **幻觉 API** | 调用了不存在的方法/参数/配置项 | typecheck + 真跑一次；文档里搜这个方法 |
| **假测试** | mock 自证、无断言、快照兜底 | 改坏实现看测试红不红 |
| **放宽断言** | 把 `assertEquals` 改成 `assertNotNull`，或删掉一条断言 | `git diff` 里看测试文件的**删除行** |
| **注释掉失败的测试** | `skip` / `xit` / 注释 / `@Ignore` | 全仓库 grep `skip`、`todo`、`xit` |
| **改无关文件** | 顺手"优化"了别处 | `git diff --stat` 对照任务卡禁区 |
| **吞异常** | `catch {}` 或 catch 后只打日志继续跑 | grep 空 catch 块 |
| **硬编码配置** | URL、密钥、路径、魔法数字写死 | grep `http://`、`localhost`、长字符串 |
| **复制粘贴** | 三处几乎相同的代码块 | 看 diff 里有没有重复的形状 |
| **文档与实现不一致** | README 说 `npm run dev`，实际是 `make dev` | 照文档做一遍 |
| **迁移不可回滚** | `down` 是空的或会丢数据 | 实际跑一次 down 再 up |
| **悄悄降级需求** | "先实现简化版"但没说 | 逐条对验收标准 |
| **过度实现** | 加了没人要的配置项、抽象层、"未来可能需要"的参数 | 对照非目标；问"哪条 REQ 要求了这个" |
| **重复造轮子** | 仓库里已经有一个了又写一个 | grep 这个功能的关键词，看是不是有两处 |
| **手搓成熟方案** | 自己写密码哈希、时区换算、CSV 解析 | 对照 `reuse.md` 第二节的表，命中即阻塞 |
| **抄了没适配** | 命名是 `User`/`data`、错误格式和本项目不一致、目录位置不对 | 读起来像不像这个项目里长出来的 |
| **锁文件冲突瞎解** | 直接删了重新生成，版本大范围变动 | 看锁文件 diff 的规模 |
| **声称完成但没验证** | "所有测试通过" | 自己跑一次 |

> **这张表是 checklist，不是待办清单。** 用法是：看到可疑的东西时，来这里对一下
> 它属于哪一类，以及怎么快速验。**没有信号就不要逐条去找**——
> 那正是这套流程自己要避免的失败模式（`proportion.md` 第六节）。
> 十五分钟的时间预算就是防这个的：超预算通常说明审得太细了，不是问题太多。

## 五、审计输出格式

审完给三类反馈，**分类比措辞重要**——AI 需要知道哪些必须改：

- **阻塞**——不改不能合。必审项的问题一律阻塞。
- **建议**——可以现在改也可以记下来，说清楚哪个。
- **记录**——不用改，但值得写进 ADR 或 runbook 的认知。

反馈要指向**行为**而不是风格：说"库存为 0 时这里会返回 500 而不是 409，
和 REQ-ORD-003 不符"，不要说"这段写得不好"。前者 AI 能直接修，后者它只会重排代码。

**收到 AI 反驳时**：如果它给出了具体的技术理由（指向代码、指向文档、指向测试），
认真核实；如果它只是道歉然后照做，反而要警惕——它可能没理解问题，
只是在顺从，改出来的东西会绕开症状而不是修因。

## 六、闸门与审计项对照

| 闸门 | 必审 | 时间预算 |
|---|---|---|
| G1 意图 | 非目标、验收标准可判定性、术语表 | 15 分钟 |
| G2 决策 | ADR 全部、依赖准入 | 20 分钟 |
| G3 骨架 | **亲手跑通** + doctor.sh + 密钥没进仓库 | 15 分钟 |
| G4 契约 | schema、迁移 down、错误码、字段单位 | 20 分钟 |
| G5 切片 | 上面第二节的六步 | 15 分钟 / PR |
| G6 上线 | 回滚演练、备份恢复演练、监控覆盖 | 30 分钟（一次性） |

全流程人的总投入在几小时量级。**这是这套流程的设计约束**——
如果审计成本超过这个量级，人就会开始跳过闸门，那流程就崩了。
