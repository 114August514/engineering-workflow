# 分寸：不过度设计，也不追幻影风险

两种失败，一个根因。

| 失败 | 长什么样 |
|---|---|
| **过度设计** | 为**不存在的需求**建抽象：只有一个实现的接口、没人用的配置项、"以后可能要换"的适配层 |
| **幻影风险** | 为**不会发生的故障**建防御：到处 try-catch、给不可能为 null 的东西判空、给单机脚本加分布式锁 |

根因相同：**用想象中的未来替代了眼前的证据。**

AI 特别容易这样，因为对它来说多写一层抽象、多加一个 catch **几乎零成本**——
但**人审它的成本是一样的**。这就直接回到整套流程的核心命题：
每一行没必要的代码都在消耗那个最稀缺的资源（人的评审精力），
同时把真正该被看见的问题埋得更深。

**最坏的情况不是多写了代码，是精力被花在了假问题上，真问题因此没人看。**

---

## 一、这个防御该不该做：三问

不要凭感觉，按顺序问三句：

1. **它发生过吗？** 在这个系统里发生过，或者在同类系统里是已知的常见模式吗？
2. **发生了会怎样？** 丢数据 / 丢钱 / 脏状态 / 用户重试一次就好 / 日志里多一行
3. **不处理的代价 vs 处理的代价？** 处理的代价不只是这几行代码——还包括
   以后每次读这段代码的时间、每次评审它的时间、**以及它自己可能引入的 bug**

对照表：

| 证据 | 后果 | 结论 |
|---|---|---|
| **发生过** | 任何 | **修**，并补一条回归测试（走 `bugfix.md`） |
| **同类系统的已知模式**（网络超时、并发写同一行、重复提交、磁盘满、时钟回拨） | 丢数据 / 丢钱 / 脏状态 | **处理**。这不是想象，是已知模式 |
| 同类系统的已知模式 | 用户重试一次就好 | **让它失败**，但保证失败可见 |
| **纯推理出来的** | 丢数据 / 丢钱 | **写进风险表，不写代码**。等到有证据或有需求 |
| 纯推理出来的 | 轻微 | **不处理，也不讨论** |

第四行是最容易被忽略的一档：**记录，而不是编码**。
把它写进 `architecture.md` 的风险表，比写进代码好——风险表是给人看的，
代码是要一直维护的。

---

## 二、"让它失败"是一个正当选择

AI 的默认倾向是所有分支都要接住。但对**没预期到的情况**：

> **大声失败 > 悄悄兜底。**

一个 catch 住然后返回默认值的地方，是把一个明显的崩溃变成一个隐蔽的数据错误。
崩溃十分钟就能定位，隐蔽的数据错误可能三个月后才被发现，而且那时已经污染了
一堆下游数据。

判据：

> **如果这里发生了我没想到的事，我希望立刻知道，还是希望它继续跑？**

绝大多数业务代码，答案是前者。

"让它失败"不等于不管——它的要求是**失败可见**：
异常往上抛、日志里有完整信息和 traceId、用户看到一个明确的错误而不是空白页。
见 `backend.md` 第五节。

## 三、过度设计的可查信号

抽象的建议没用，下面这些是能直接看出来的：

| 信号 | 判据 |
|---|---|
| 接口/抽象基类**只有一个实现** | 那这个接口没有存在的理由 |
| "通用"工具函数只被调用一次，且参数超过 3 个 | 它在服务一个想象中的第二个调用者 |
| 配置项**没有任何一处使用非默认值** | 它不是配置，是伪装成配置的常量 |
| 插件机制 / 策略模式 / 工厂，但只有一个策略 | — |
| 包装第三方库的适配层，理由是"将来可能换" | 真要换的时候，这层适配也一定不合适 |
| 缓存 / 连接池 / 批处理，但**没测过慢** | 提前优化 |
| 代码里出现 spec 和非目标都没提过的能力 | 直接问：哪条 REQ 要求了这个 |

**总判据：删掉这一层，代码会变短吗？会变难懂吗？**
变短且不变难懂 → 删。

**三次法则**：同样的东西出现**第三次**再抽象。第二次先老实复制。
在只有一个用例的时候做的抽象，几乎必然是错的——因为你还不知道
哪部分是共性、哪部分是这个用例特有的。

## 四、给人的：怎么打断 AI 的过度设计

五句话，比讲道理有效：

- **「哪条 REQ 要求了这个？」** —— 对不上就删
- **「这个情况实际发生过吗？」** —— 逼它区分证据和推理
- **「删掉这层会怎样？」**
- **「不处理这个，最坏是什么？」** —— 逼它说出后果，而不是笼统的"不安全"
- **「现在有几个实现？」** —— 一个就别抽象

反过来，AI 汇报时应该主动说：

> **「我考虑过但故意没处理的情况」**：
> 支付网关返回未知状态码——没见过，且发生了会走人工对账，不值得现在写分支。
> 已记进风险表。

这一节和"我最不确定的三个地方"是一对：一个说我在哪里可能错了，
一个说我在哪里**故意没做**。两个都写出来，人才审得准。

## 五、对称的失败：别把"简单"当借口

这份文档不是用来拒绝所有工程实践的。下面这些**不是过度设计**，不许省：

- 服务端的输入校验（前端那份是体验，服务端那份是安全）
- 钱、库存、配额的并发控制
- 迁移的 `down`
- 密钥不进仓库
- 错误可见：日志 + traceId
- 备份能恢复（演练过）
- 不变量落到数据库约束

**它们的共同点：出事了不可逆，或者非常贵。**

于是整份文档收敛成一条，和整套流程同一条主线：

> **按可逆性决定投入。**
> 不可逆的（数据、钱、契约、权限）——防。
> 可逆的、便宜的、能重试的——让它失败，保证失败可见。

## 六、这套流程自身的分寸

同样的标准要用在这套流程上，否则它会变成新的仪式：

- **分流表存在的意义就是这个**——不是所有改动都值得走全流程
- **`audit.md` 的失败模式表是 checklist，不是待办清单。**
  没有信号就不要逐条去找。它的用法是：看到可疑的东西时，去表里对一下这是哪一类
- **`review.sh` 报的是信号，不是缺陷。** "这个文件 500 行"不等于"这个文件有问题"，
  它只是提示你去看一眼。看完觉得合理，就放着
- **闸门有时间预算**（`audit.md` 第六节）。超预算通常说明这次审得太细，
  而不是说明问题太多
- 如果某个环节持续没有发现过任何真问题，**删掉它**

**如果这套流程本身开始妨碍交付，砍掉它的一部分，并写一份 ADR 说明为什么。**
流程是工具，不是目的。
