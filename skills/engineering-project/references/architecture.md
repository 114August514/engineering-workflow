# P2 架构与决策

**目标**：定下不可逆的技术决策，并留下"为什么"。
**产物**：`docs/decisions/NNNN-<短标题>.md` + 一张容器图 + 风险排序
**闸门**：G2——人审 ADR

**为什么闸门设在这里**：代码可逆，决策不可逆。选错了数据库、选错了认证方案、
选错了部署形态，改回来的成本是重写；而一段写丑了的函数，改它是十分钟。
所以人有限的审计精力应该花在 ADR 上，而不是逐行看实现。

---

## 一、ADR：AI 最容易丢的东西

AI 记得代码长什么样，不记得**为什么这么选**。三周后它会"顺手优化"掉一个
你为了绕过某个坑而写的怪写法。ADR 就是防这个的。

一份 ADR 一个决策，`docs/decisions/0001-choose-postgres.md`：

```markdown
# 0001. 用 PostgreSQL 而不是 SQLite

- 状态：已接受
- 日期：2026-07-26

## 背景
需要存订单和库存，有并发扣减。预计一年内数据量 < 100 万行。
部署在单台 VPS 上，运维只有我一个人。

## 选项
1. SQLite —— 零运维，单文件备份。但写并发靠全库锁，扣库存会成为瓶颈。
2. PostgreSQL —— 行级锁，事务能力够。多一个要运维的进程。
3. MySQL —— 与 2 相当，但我不熟。

## 决定
选 PostgreSQL，用 Docker Compose 起，和应用同机。

## 后果
- 好：库存扣减可以用 `SELECT FOR UPDATE`，不用在应用层做锁
- 坏：备份从"拷一个文件"变成"跑 pg_dump"，需要写进 runbook
- 坏：本地开发需要装 Docker
- 反悔成本：中。ORM 层隔离了方言，但迁移脚本要重写
```

### 什么时候必须写 ADR

任一条成立就写：

- **不可逆或反悔很贵**（数据库、语言、部署形态、认证方案、消息中间件）
- **影响多个模块**（错误处理约定、鉴权方式、时间与时区处理、ID 生成策略）
- **后来者一定会问"为什么不用更常见的那个"**（你偏离了默认选择）
- **你在两个方案之间犹豫超过十分钟**

反过来：用哪个日期库、目录叫 `utils` 还是 `lib`——不写，写了是噪音。

### 决策变了怎么办

**不要改旧 ADR。** 新写一份，旧的状态改成"被 NNNN 取代"。历史决策的
上下文本身是有价值的——它记录了当时的约束。

## 二、选型：默认收敛，不给无限选择权

AI 面对开放选择时会给出一个"看起来很全面"的方案，通常引入过多东西。
按这个顺序收敛：

1. **这个仓库里已经在用什么？** 已有的优先，哪怕不是最好的。
   一个仓库里有两套做同一件事的工具，就是长期的税。
2. **这台机器/这个人已经熟什么？** 运维成本主要来自不熟悉。
3. **最无聊的那个能不能满足？** 参照验收标准和约束里的数字，
   不要按想象中的规模选型。
4. 前三条都不能决定，才去比较。

### 新增依赖的准入检查

**先确认真的需要新依赖**——按 `reuse.md` 的四层检索走一遍：
这个仓库里已经有了吗 → 标准库里有吗 → 已装的依赖里有吗 → 才轮到加新的。

确实要加，问五句（`audit.sh` 会把依赖文件变更标成必审）：

- 最近一年有提交吗？未解决 issue 堆积吗？
- 许可证兼容吗？
- 它自己又拖进来多少间接依赖？
- 我用得到它的多少？为 1% 的功能引入一整个框架不划算。
- 万一它弃维了，切换成本多大？

**"自己写 50 行能不能替代"只对边界情况可枚举的小工具成立。**
安全、时间与时区、协议与格式解析、金额精度、重试退避这些，
**一律用成熟实现**——它们的共同点是错了很贵，而且错误不会立刻显现。
清单见 `reuse.md` 第二节。

判据：**这个东西的边界情况我能列全吗？** 列不全就别手搓。

### 架构风格：先分层，别急着上花样

默认从最朴素的开始：

```
接口层（HTTP/CLI）  →  只做协议转换和参数校验，不含业务判断
应用层（用例）      →  编排：调领域、开事务、发事件
领域层（业务规则）  →  纯函数为主，不碰 IO —— 这一层最值得写密集的单元测试
基础设施层（IO）    →  数据库、外部 API、文件、消息
```

关键约束只有一条：**领域层不依赖基础设施层**（依赖方向永远朝内）。做到这一条，
业务规则就能被又快又密地测试，AI 在这一层的产出也最容易验证。
这就是 Hexagonal / Ports & Adapters 的实用版本，不需要引入那一整套术语。

微服务、CQRS、事件溯源、消息队列——**在 P2 一律默认不用**。
除非有一条具体的验收标准或约束逼你用，并且你为它写了一份 ADR。

## 三、容器图：一张图，只画进程和数据

C4 模型四层里只画第二层（Container）。回答三个问题就够：

- 有哪些**会独立运行的东西**（Web 服务、后台任务、定时器、数据库、缓存）
- 谁**存**数据，存在哪
- 谁**调**谁，同步还是异步

```
[浏览器] ──HTTPS──► [Web 服务 :8080] ──SQL──► [PostgreSQL]
                          │
                          └──HTTP──► [支付网关（外部）]
[定时任务] ──────────────────SQL──────► [PostgreSQL]
```

纯文本画就行。**不要画类图**——代码结构会变，画了就过期，而且 AI 可以随时
从代码里重新读出来。容器图不一样，它反映的是部署形态，变得慢，且很难从代码里看出来。

## 四、风险排序：先做最不确定的

新项目失败的典型方式：把简单的部分做得很漂亮，最后两周才发现最难的那块
根本行不通。

把所有"我不确定能不能成"的事情列出来，按**不确定性 × 影响**排序，
**排在最前面的必须在 P3 骨架里就打通**：

```markdown
## 风险
| 风险 | 不确定性 | 影响 | 何时验证 | 验证方式 |
|---|---|---|---|---|
| 第三方支付回调能否在内网环境收到 | 高 | 致命 | P3 骨架 | 打通一次真实沙箱回调 |
| 单机 Postgres 能否扛住扣库存并发 | 中 | 高 | P3 骨架 | 压一次 200 并发 |
| 富文本编辑器能否满足编辑需求 | 中 | 中 | P5 首片 | 做一个最小可用版本 |
| 邮件送达率 | 低 | 低 | 上线后 | 观察 |
```

这就是 Walking Skeleton 要挑哪条链路的依据：**挑穿过最高风险的那条**，
而不是最容易实现的那条。
