# 人机对接

怎么让人和 AI 交换信息时损耗最小。分三部分：**项目宪法**（长期）、
**任务卡**（单次）、**上下文管理**（会话）。

---

## 一、`AGENTS.md`：项目宪法

放仓库根目录。**每个 agent 开工前必读**，所以它必须短——
超过 150 行就没人（和没模型）会认真读完。

### 该写什么

只写**不会很快过期、且从代码里看不出来**的东西：

```markdown
# <项目名>

一句话说这是什么。

## 验证
提交前必须跑：`make check`
它包含格式检查、lint、类型检查、测试。**不要另外发明命令。**

## 目录
- `src/<上下文>/` —— 按限界上下文分，不按技术层分
- `src/*/domain/` —— 纯业务规则，**不许 import 任何 IO**（数据库、HTTP、文件）
- `contracts/`、`migrations/` —— 改动前必须先问人
- `docs/spec.md` 验收标准 / `docs/glossary.md` 术语 / `docs/decisions/` 为什么这么设计

## 命名
所有概念用 `docs/glossary.md` 里的名字。需要新概念时先往术语表加一行。

## 不变量
写代码时不能违反 `docs/glossary.md` 的 INV-* 条目，数据库约束是最后一道防线。

## 禁止
- 不许改 `contracts/`、`migrations/`、认证相关代码 —— 先提出来让人决定
- 不许新增依赖 —— 先说明为什么，以及自己写 50 行能不能替代
- 不许 skip / 注释掉失败的测试；测试红了就是代码错了
- 不许在错误里用临时字符串，错误码登记在 `contracts/errors.md`
- 提交信息用 `<类型>: <做了什么>`，不要写"更新代码"

## 汇报
完成时说清楚：做了什么 / 没做什么 / 怎么验证的 / 哪里不确定 / 碰了哪些文件。
不确定就说不确定，不要用"应该没问题"收尾。
```

### 不该写什么

- **会过期的实现细节**（"UserService 有个 findByEmail 方法"）——
  代码变了文档不会变，过期的宪法比没有宪法更糟
- **能从代码看出来的**（依赖列表、目录树全展开）
- **通用编程建议**（"写清晰的代码"、"注意性能"）——占篇幅，不产生行为差异

判据：**这一条会改变 AI 的行为吗？** 不会就删掉。

## 二、任务卡：单次交接的标准格式

格式见 `slices.md`。这里说**为什么每一节都不能省**：

| 节 | 省掉会怎样 |
|---|---|
| 背景 | AI 不知道边界在哪，会做一个"更通用"的版本 |
| 验收标准 | 完成判定变成主观的，AI 会宣称完成 |
| 约束 | 它会重新发明已有的东西，或改掉你不想动的设计 |
| 验证 | 它会用自己发明的方式验证，或者根本不验证 |
| **禁区** | 它会顺手"优化"旁边的代码，PR 膨胀，人审不动 |

## 三、人该怎么提需求

给人看的一节。三条：

### 1. 给例子，不给形容词

| 不要说 | 改成说 |
|---|---|
| "做个用户友好的上传功能" | "拖一个 50MB 的 zip 进来，显示进度条；超过 100MB 直接拒绝并说明限制" |
| "性能要好" | "列表页 1000 条数据，首屏 1 秒内出来" |
| "要稳定" | "支付网关挂了的时候，订单要保住，用户看到'稍后重试'而不是 500" |

形容词会被 AI 各自解读，例子不会。

### 2. 说清楚不做什么

比说做什么更重要。AI 的默认倾向是**多做**——它会加配置项、加抽象层、
加"未来可能有用"的参数。你不划边界，它就自己划。

### 3. 说清楚禁区

"不要动登录那块"、"不要改数据库结构"、"不要引入新库"。
这三句话能挡掉大部分让 PR 变得无法评审的情况。

## 四、AI 该怎么汇报

固定五段（见 `slices.md` 的例子）。重点是后两段：

- **"没做什么"**——把范围外的、降级处理的、留给下次的说清楚。
  AI 最常见的沟通失败是**默认省略**：简化了一个地方但没提，
  人以为做完了，三周后在生产环境发现。
- **"哪里不确定"**——这一节直接告诉人该重点审哪里。
  如果 AI 每次都说"没有不确定的"，那它不是在找问题。

**禁止用"应该没问题"、"看起来是对的"收尾。** 要么验证过并贴出证据，
要么明说没验证。

## 五、上下文管理

长任务里，信息会从会话里流失。四条应对：

### 1. 结论写回文件，不要留在对话里

会话会结束、会被压缩、会开新的。凡是"下次还需要知道"的东西——
决定、发现的坑、被否掉的方案及原因——立刻写进 `docs/decisions/`
或 `docs/runbook.md`。

判据：**这个信息如果丢了，下次要重新花时间搞明白吗？** 是就落盘。

**在途的工作**落在 `docs/journal/`：开工前先写意图（预写日志），
会话死在半路时下一个人能接得上。仓外副作用（跑过的迁移、发过的部署）
必须写在那里——`git revert` 撤不掉它们。见 `journal.md`。

### 2. 接手时先看在途

新会话开场三十秒固定做三件事：`make journal`（有没有在途的、是不是我的）、
`git status`（工作区干净吗）、`git log --oneline -5`（做到哪了）。
三者对不上就先对齐，**不要在状态不明时开始写新代码**。

### 3. 一个会话做一件事

一条切片一个会话。做完、合并、开新的。理由：
上下文里堆着上一个任务的细节，会让 AI 在新任务里做出基于旧假设的判断。

会话已经很长、AI 开始重复犯之前纠正过的错误、或者开始"忘记"约束时，
就是该开新会话的信号——把当前状态写进文件，重开。

### 4. 给 AI 的上下文要收窄

任务卡限定在**一个限界上下文**内。这就是 P1 划边界在 AI 协作里的实际价值：
agent 只需要读一个目录就能完成任务，不需要理解整个系统。
上下文越窄，产出质量越高。

## 六、这套东西怎么防 spec 漂移

SDD 的公认短板是 spec 和代码会悄悄不一致。我们的应对是**机械可查**的：

1. 每条验收标准有 `REQ-ID`
2. 实现它的测试，名字里必须出现这个 ID
3. `make audit` 做双向检查：
   - **孤儿需求**：spec 里有 ID，测试里搜不到 → 没做，或做了没测
   - **孤儿测试**：测试引用了 spec 里不存在的 ID → spec 过期，或在做范围外的事

不依赖任何人的自觉。需求变更时，改 spec 会立刻让 audit 报出不一致，
逼你同步改测试。
