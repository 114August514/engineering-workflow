# 三条横切规则

**不管你在写前端、后端、接口还是脚手架，这三条都成立。**

它们单独成一份，是因为四个卫星 skill 和主 skill 的快速路径都要指向它——
写四遍就一定会有三份过期。

---

## 1. 先搜再写

写任何一段有名字的功能之前，按顺序找一遍：

1. **这个仓库里已经有了吗** —— `grep -rn "关键词" src/`
   AI 最常见的重复造轮子不是引错库，是**仓库里已经有一个了又写一个**
2. 标准库 / 运行时里有吗
3. 已经装了的依赖里有吗
4. 才轮到新增依赖，而且要先说明理由

**这些一律用成熟实现，不许手搓**：密码哈希与加密、token 签发校验、随机数、
时区与日期换算、HTTP/JSON/CSV/URL 解析、金额精度、重试退避、限流、
数据库驱动与迁移工具。判据：**这个东西的边界情况我能列全吗？** 列不全就别写。

抄进来的必须**适配**：命名换成术语表里的词、删掉用不到的部分、
错误走统一信封、放进正确的目录。**看不懂的代码不要抄。**

→ 展开见 `reuse.md`

## 2. 先写测试，并且亲眼看它红

```
写测试 → 跑，看它红（失败原因要对）→ 最小实现 → 跑，看它绿 → 清理 → make check
```

**第二步不能跳。** 没见过失败的测试可能什么都没断言。写完实现再补测试时，
几乎必然写出"刚好能过"的测试——**测试看起来很多，实际什么都没保证**。

测试名里带 `REQ-ID`。除了正常路径，专门写：不变量违反、非法状态迁移、
spec 里每条「如果……那么……」。

→ 展开见 `slices.md` 第三、四节

## 3. 不过度设计，也不为没发生过的故障写防御

**按可逆性决定投入**：

- 不可逆或很贵的（数据、钱、契约、权限、迁移、密钥）→ 防住
- 可逆的、能重试的 → **让它失败**，但保证失败可见（异常往上抛 + 日志 + traceId）

没预期到的情况，**大声失败好过悄悄兜底**——`catch` 住返回默认值，
是把一个十分钟能定位的崩溃，变成三个月后才发现的数据污染。

加一层抽象 / 一个配置项 / 一段防御之前，先回答：
**哪条 REQ 要求了这个？这个情况实际发生过吗？删掉它会怎样？** 答不上来就别加。

纯推理出来的风险 → 写进风险记录，不写进代码。

→ 展开见 `proportion.md`

---

## 完成时怎么汇报

说清六件事，不要只说"做完了"：做了什么 / **没做什么** / 怎么验证的（贴 `make check`
输出）/ **哪里不确定**（写满三条）/ **故意没处理的** / 碰了哪些文件。

不要用"应该没问题""看起来是对的"收尾。要么验证过并给出证据，要么明说没验证。
