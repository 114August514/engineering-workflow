# P6 交付与运维

**目标**：能反复、安全、可回滚地上线，出事能查、能恢复。
**产物**：`docs/runbook.md` + 监控 + 备份
**闸门**：G6——"炸了怎么回滚"

注意 P3 就已经部署过了。这一阶段做的是把**一次性的部署**变成
**可重复、可回滚、可观测的交付**。

---

## 一、环境

三个，不要更多：

| 环境 | 用途 | 数据 |
|---|---|---|
| 本地 | 开发 | 假数据，`make seed` 一键灌 |
| 预发 | 合并前验证 / 演示 | **脱敏**的样本数据，绝不用生产数据副本 |
| 生产 | 真的 | 真的 |

**三个环境的部署方式必须一样**（同一个 `make ship`，只是变量不同）。
"生产用了不同的部署方式"是事故的经典来源。

### 配置（12-Factor 的实用部分）

- 配置**全部**从环境变量读，代码里不出现任何环境相关的值
- 代码里不出现 `if (env === 'production')` 的业务分支——
  差异靠配置项表达，不靠代码分支
- **启动时校验所有必需配置**，缺一个就退出并明确说缺哪个。
  不要让它跑到第一个请求才失败
- `.env.example` 有全部键名 + 说明 + 示例格式，**没有真实值**

### 密钥

- 永远不进仓库。已经进过就当它泄露了：**换掉它**，不是删掉那次提交就完事
- 用平台的密钥管理（或至少是不进仓库的环境变量文件）
- 定期轮换的流程写进 runbook
- CI 的密钥用最小权限，部署密钥和开发密钥分开

## 二、发布

### 原则

- **小步、频繁、可回滚**。一次发一条切片，比攒两周发一次安全得多——
  出问题时的排查范围是线性的
- **发布和启用分开**：代码可以先发上去但关着（特性开关），
  确认没问题再打开。这样"回滚"变成"关个开关"，秒级
- 发布过程幂等，中途失败不能留下半个状态

### 数据库迁移与发布的顺序

这是最容易出事的地方。规则：**迁移必须向前兼容一个版本**。

```
错误做法：一次发布同时改 schema 和代码
  → 滚动更新期间，新旧代码同时在跑，旧代码遇到新 schema 就炸

正确做法（加字段）：
  1. 发迁移：加可空新列                    ← 旧代码不受影响
  2. 发代码：双写新旧列，读旧列
  3. 回填历史数据
  4. 发代码：读新列
  5. 发迁移：删旧列（可以等很久）
```

**每一步都能单独回滚。** 麻烦，但这是唯一不会在半夜出事的做法。

---

## 三、回滚

**回滚方案没演练过就等于没有。** G6 闸的核心就是这一条。

runbook 里写清楚三种情况：

| 情况 | 怎么办 |
|---|---|
| 代码有问题，数据没变 | 部署上一个版本。**要有确切命令，不是"重新部署旧版本"** |
| 代码有问题，且已经写了新格式数据 | 这就是为什么迁移要向前兼容。回滚代码，数据留着，新列先不用 |
| 迁移本身有问题 | 跑 `down`。**前提是你验证过它** |

演练方式：在预发环境真的部署一次、真的回滚一次、**计时**。
知道"回滚要 4 分钟"和以为"应该很快"是两回事。

---

## 四、监控：先做能回答问题的最小集

不要一上来上全套。按"出事时你会问什么"来配：

| 你会问 | 需要什么 |
|---|---|
| 还活着吗 | 健康检查 + 探活告警 |
| 是不是在报错 | 错误率（按错误码分组）+ 突增告警 |
| 是不是变慢了 | 关键路径 p95 延迟 |
| 是谁的问题 | 结构化日志 + traceId 串联 |
| 什么时候开始的 | 部署事件打在同一个时间轴上 |

**告警只配"需要有人立刻起床"的那几条。** 告警太多等于没有告警——
一个月内被误报叫醒三次，人就会把通知静音，然后错过真的那次。

日志保留多久、存哪、怎么搜，写进 runbook。

## 五、备份

**恢复演练过才算有备份。**

- 备份什么：数据库、用户上传的文件、密钥（分开存）
- 多久一次、保留多久：写进 runbook
- **至少演练一次完整恢复**：从备份起一个新库，跑一次应用，能用
- 记录 RPO（最多能丢多久的数据）和 RTO（恢复要多久），
  确认这两个数字你能接受

没恢复演练过的备份，在真需要的时候有很大概率是坏的、不全的、或者你不知道怎么用。

---

## 六、依赖与安全基线

- CI 里跑依赖漏洞扫描，**高危挡住合并**（这是免审项，机器把关）
- 依赖更新有节奏：定期小步升，不要攒一年一次大升
- 锁文件进仓库
- 基础安全：HTTPS、安全响应头、限流、输入校验在服务端、
  不在错误里泄露内部信息、上传文件校验类型和大小

## 七、`docs/runbook.md` 骨架

```markdown
# 运维手册

## 部署
- 命令：`make ship`
- 需要的环境变量：见 .env.example
- 耗时：约 X 分钟
- 怎么确认成功：访问 /healthz 返回 200，且版本号是新的

## 回滚
- 命令：<确切命令>
- 耗时：X 分钟（演练于 2026-07-26）
- 涉及数据库迁移时：<具体步骤>

## 出事了看哪里
- 日志：<地址，怎么按 traceId 搜>
- 监控面板：<地址>
- 常见故障与处理：<一条一条积累>

## 备份与恢复
- 备份：<什么时候、存哪、保留多久>
- 恢复步骤：<确切命令>
- 上次恢复演练：2026-07-26，耗时 X 分钟

## 密钥
- 存在哪、谁有权限、怎么轮换
```

## 八、出口检查（G6 闸）

- [ ] 回滚**实际演练过**并记了耗时
- [ ] 备份恢复**实际演练过**
- [ ] 迁移是向前兼容的（滚动更新期间新旧代码能共存）
- [ ] 告警能到人（发一条测试告警确认收得到）
- [ ] `.env.example` 完整，缺配置时启动会明确报错
- [ ] runbook 里每条命令都是可以直接复制执行的
- [ ] 依赖漏洞扫描在 CI 里，且会挡合并
