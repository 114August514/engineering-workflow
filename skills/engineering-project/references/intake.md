# P0 意图澄清

**目标**：把"我想做个 X"压成一页**可验收**的意图。
**产物**：`docs/spec.md`
**闸门**：G1——人确认非目标与验收标准（连同 P1 的术语表一起审）

这一步是全流程杠杆最高的地方。这里模糊一分，后面返工十分。

---

## 一、先问，别猜

AI 最常见的失败不是写错代码，是**脑补需求然后写了一堆对的代码去解决错的问题**。

问题按"回答会不会改变设计"排序，不改变设计的不要问：

| 优先级 | 问题 | 为什么问 |
|---|---|---|
| 必问 | 谁用？他用完之后**什么变了**？ | 没有行为改变就没有价值，功能可以砍 |
| 必问 | **什么明确不做**？ | 见下面第三节 |
| 必问 | 怎么算做完？拿什么判定？ | 直接决定验收标准 |
| 必问 | 失败了会怎样？（丢数据 / 用户等一会 / 没人发现） | 决定要投多少工程量在可靠性上 |
| 高 | 数据从哪来、有多少、增长多快 | 决定存储与架构，且改起来最贵 |
| 高 | 谁能看谁能改？有没有隐私/合规约束 | 权限模型后加最痛 |
| 高 | 部署到哪？谁运维？ | 决定整个交付链路 |
| 中 | 什么时候要？可以砍什么换时间 | 决定切片顺序 |
| 中 | 有没有必须兼容的既有系统/格式 | 约束契约 |

**提问节奏**：一次问一组同类的（2—3 个），不要一次甩十个，也不要一次只问一个
拖二十轮。用户答"随便/你决定"时，给一个默认值让他否决，不要再追问。

## 二、验收标准用 EARS 句式

自然语言写的需求没法判定，写成 EARS（Easy Approach to Requirements Syntax）
五种句式之一就能判定。Kiro 的 `requirements.md` 用的就是这套。

| 类型 | 句式 | 例 |
|---|---|---|
| 普遍 | 系统应当 `<响应>` | 系统应当以 UTC 存储所有时间戳 |
| 事件驱动 | **当** `<触发>` 时，系统应当 `<响应>` | 当用户提交订单时，系统应当返回订单号 |
| 状态驱动 | **在** `<状态>` 期间，系统应当 `<响应>` | 在维护模式期间，系统应当对写请求返回 503 |
| 可选特性 | **若** `<特性启用>`，系统应当 `<响应>` | 若启用了邮件通知，系统应当在下单后发确认信 |
| 非期望行为 | **如果** `<异常>`，那么系统应当 `<响应>` | 如果支付网关超时，那么系统应当保留订单为待支付并重试三次 |

**最后一种最容易被漏，也最容易出事故。** 每写三条正常路径，强制自己写一条
"如果……那么……"。

### 每条标准配一个具体例子

这是 Specification by Example 的核心：抽象描述会被各自解读，具体例子不会。

> REQ-ORD-003 当用户提交订单时，系统应当在库存不足时拒绝并返回明确原因。
> 例：商品 A 库存 2，用户提交数量 3 → 返回 `409 OUT_OF_STOCK`，
> 消息含"库存仅剩 2"，订单不落库。

只要用户说了形容词（"快"、"友好"、"稳定"、"智能"），就回问一句"举个例子"，
把它换成数字或一次具体交互。

### REQ-ID

每条标准一个 ID：`REQ-<模块缩写>-<三位序号>`，例如 `REQ-ORD-003`。

**规则：实现这条标准的测试，函数名或描述里必须出现这个 ID。**
`scripts/audit.sh` 靠它做双向追溯，查出：

- **孤儿需求**：spec 里有、没有任何测试引用 → 要么没做，要么没测
- **孤儿测试**：测了一个 spec 里不存在的东西 → 要么 spec 过期，要么在做范围外的事

这是我们对 SDD 已知短板（spec 与 code 悄悄漂移）的应对，比"定期人工对一遍"可靠。

## 三、非目标必须写满

**空的非目标一律视为这一步没做完。**

非目标不是"以后再说的功能列表"，是**用来挡住 AI 和你自己的护栏**。AI 在实现时
遇到分叉会倾向于"顺手都支持一下"，非目标就是让它停手的依据。

至少覆盖这几类：

- 不支持的场景（"不做多租户"、"不支持离线"）
- 不做的规模（"不考虑单表超过 100 万行"）
- 不做的兼容（"不支持 IE"、"不兼容 v1 接口"）
- 不自己造的东西（"不自建认证，用 OAuth 提供方"）
- 明确延后的（"搜索先用 LIKE，不上全文索引"）

每条非目标最好带一句"如果将来要做，从哪改"——避免把非目标写成死路。

---

## 四、范围过大时先拆

如果需求描述里出现多个**互相独立**的子系统（"要有聊天、文件存储、计费和数据
看板"），不要往下细化——先拆。

拆的方法：找出哪些部分**可以独立上线并单独产生价值**。每个部分走自己的
P0→P6 循环。先做哪个，按"最不确定的先做"排（见 `architecture.md` 的风险排序），
不是按最容易的先做。

一份 spec 对应一个可独立交付的东西。一页写不下就是没拆干净。

## 五、`docs/spec.md` 骨架

```markdown
# <项目名>

## 问题
<两三句：现在什么情况、什么地方不成立、为什么值得解决>

## 用户与场景
<谁、在什么时候、为了什么用它>

## 成功判定
<上线后看什么指标/什么现象，就说明这事做成了>

## 非目标
- 不做 ……（若将来要做：从 …… 改起）
- 不做 ……

## 验收标准

### <模块名>
- **REQ-XXX-001** 当 …… 时，系统应当 ……
  - 例：……
- **REQ-XXX-002** 如果 …… 那么系统应当 ……
  - 例：……

## 约束
<部署环境、必须兼容的东西、合规、预算、时间>

## 未决问题
<还没定的，标明"谁在什么时候之前定"。这一节必须在 P2 之前清空>
```

## 六、这一步的反模式

| 现象 | 为什么是问题 | 怎么办 |
|---|---|---|
| AI 直接开始写代码 | 需求还没定，写的都是猜的 | 停下，回到提问 |
| 验收标准里有"友好""高效""合理" | 无法判定，等于没写 | 要例子，换成数字或具体交互 |
| 非目标为空 | 范围会在实现中无声膨胀 | 至少写五条 |
| 一次问用户十个问题 | 人答不动，会敷衍 | 一次 2—3 个同类 |
| 把技术方案写进 spec | spec 是"做什么"，方案是 P2 的事 | 挪到 ADR |
| 未决问题一直挂着 | 到实现阶段会被 AI 随手替你决定 | G2 之前必须清空 |

---

## 出口检查

进 P1 之前，逐条确认：

- [ ] 问题陈述不含技术方案
- [ ] 每条验收标准是 EARS 五句式之一，且有 REQ-ID
- [ ] 每条验收标准配了具体例子（含数字或具体输入输出）
- [ ] 至少有一条"如果……那么……"的异常路径
- [ ] 非目标 ≥ 5 条
- [ ] 未决问题都标了责任人和期限
- [ ] 整份 spec 一页内读得完

然后进 P1 做术语表，**两份一起交给人过 G1 闸**。
