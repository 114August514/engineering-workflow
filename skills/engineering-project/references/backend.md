# 技术专题：后端

与语言无关。讲的是**结构和决策**，不是某个框架的用法——框架用法查官方文档，
但下面这些查文档查不到，而且做错了要重写。

按"后期最难补"排序，前三节是不可逆的。

---

## 一、鉴权：越权是 API 风险第一位

OWASP 把 **Broken Object Level Authorization**（改一下 URL 里的 ID 就能看别人数据）
列为 API 风险第一名。它简单、常见、且后果直接是数据泄露。

**AI 写出这个漏洞的默认概率很高**，因为最自然的写法就是错的：

```
❌ SELECT * FROM projects WHERE id = ?
✅ SELECT * FROM projects WHERE id = ? AND owner_id = ?
```

第一种在功能测试里完全正常——你用自己的账号点，看到的都是自己的数据。
只有**换个账号带别人的 ID** 才会暴露。

### 三层分工，一层都不能省

| 层 | 负责 | 落法 |
|---|---|---|
| middleware | **这个人是谁** | 解析 token/session → 用户身份 |
| service | **他能做这类操作吗** | 角色/权限判断 |
| **repository** | **他能碰到哪些数据** | **每个查询都带归属过滤** |

第三层最容易被忘，也最关键。**把过滤写进 repository 的方法签名里**，
让"忘记传 owner_id"变成编译错误或至少是显眼的：

```
❌ findById(id)                    ← 谁都能查任何一条
✅ findByIdForUser(id, userId)     ← 忘了传就编译不过
```

### 必须有的测试

`slices.md` 说要写异常路径，鉴权这里的异常路径是固定四条：

```
未登录访问          → 401
登录了但没权限      → 403
用别人的资源 ID     → 403 或 404（选一种，全项目统一）
自己的资源          → 200
```

**第三条是最重要的一条测试，也是 AI 最不会主动写的。**
每个涉及资源的接口都要有。

> 403 还是 404？统一选 404 能少泄露一点信息（对方不知道这个 ID 存不存在），
> 但排查时更难。定一个写进 `contracts/errors.md`，别一半一半。

## 二、ID 设计：暴露自增主键是不可逆的错误

```
❌ /api/orders/1, /api/orders/2, /api/orders/3
✅ /api/orders/ord_8f3k2m
```

自增 ID 有两个问题，且都是后期改不动的：

1. **可枚举** —— 配合上面的越权漏洞就是批量拖库。即使鉴权没问题，
   `id=1..10000` 也能探出你有多少订单
2. **泄露业务信息** —— 竞争对手看你的注册 ID 增长就知道你一周涨多少用户

规则：

- **对外 ID 和数据库主键分开**：内部自增无所谓，对外用不可枚举的 ID
- **带类型前缀**（`ord_` `usr_` `proj_`）—— 出问题时一眼看出是什么，
  也防止把用户 ID 传进订单接口
- **ID 是字符串**，别让前端当数字处理（超过 2^53 会精度丢失）
- 用 UUID / ULID / 雪花 ID 都行，**ULID 有个额外好处：按时间有序，索引友好**

**为什么这条必须在 P4 契约阶段定死**：改 ID 格式 = 改所有接口 + 所有前端 +
所有存量数据 + 所有外部集成方。这是典型的"不可逆，所以要防"（`proportion.md`）。

## 三、幂等性：网络会抖，用户会双击

这些接口**一定**会被重复调用：

```
创建订单 · 支付回调 · 发邮件 · 上传文件 · 扣额度 · 邀请成员 · 创建任务
```

原因：用户双击、前端重试、网关重试、第三方回调重发、部署时请求重放。

**"前端禁用了按钮"不算解决**——那只挡住了一种情况。

### 三种做法，按成本从低到高

| 做法 | 适用 | 怎么做 |
|---|---|---|
| **唯一约束** | 天然有唯一键 | 数据库唯一索引，冲突时返回已有资源而不是报错 |
| **Idempotency-Key** | 创建类接口 | 客户端生成 key 放 header，服务端存 key→结果，重复请求直接返回上次结果 |
| **状态机** | 有明确状态流转 | `已支付` 的订单再收到支付回调直接忽略（见 `domain.md` 的状态机） |

第三方回调（支付尤其）**必须**做去重，而且要考虑**乱序**：
先收到"支付成功"再收到"支付中"是常态。按事件时间戳或状态机决定，不要按到达顺序。

判据：**这个接口被连续调用两次，第二次的结果和数据库状态应该和只调一次完全一样。**
写一条测试直接验它。

## 四、分层与依赖方向

```
接口层  handler / route
   ↓    只做：解析请求、格式校验、调用用例、把结果和错误转成 HTTP
应用层  usecase / service
   ↓    只做：编排。开事务、按顺序调领域函数、发事件
领域层  domain
   ↑    业务规则。纯函数为主。**不 import 任何 IO**
基础设施 infra —— 数据库、外部 API、文件、消息队列、时钟、随机数
```

**唯一的硬约束：依赖方向朝内，领域层不依赖基础设施层。**

收益：领域逻辑能用**纯单元测试**密集覆盖（不用起数据库，毫秒级，可以写几百条）；
AI 在这一层的产出最容易验证（输入 → 输出，没有隐藏状态）；换数据库不影响业务规则。

怎么做到：领域层需要外部数据时，**由调用方传进来**，不要自己去取。

```
❌ 领域函数内部 await db.query(...)
✅ 应用层先查好，把数据作为参数传给领域函数
```

**时钟和随机数也算 IO。** `now()` 和 `random()` 写在领域逻辑里，
那段逻辑就没法确定性测试。当参数传进去。这是 AI 特别容易忽略的一点。

### DTO / Domain / DB Model 要分开

很容易出现"一个结构体到处用"，然后：

- 数据库加个字段，接口响应莫名其妙多了一个
- **密码哈希、内部权限标记跟着 serialize 出去了** ← 真实事故来源
- 前端要改个字段名，得动数据库

三者职责不同，就该是三个类型：

```
DTO          —— API 的请求/响应形状，对外稳定
Domain Model —— 业务内部模型，带不变量
DB Model     —— 数据库行，跟着 schema 变
```

小项目可以让 Domain 和 DB Model 暂时合并，**但 DTO 一定要独立**——
它是对外契约，不能因为内部重构就变。

## 五、handler 里不写业务判断

最常见的后端腐化方式：业务规则散在 handler 里，同一条规则在三个接口里各写一遍，
其中两个是错的。

判据：**handler 里出现 `if` 判断业务条件，就该挪走。**

```
❌ handler: if (user.level === 'vip' && order.amount > 100) { discount = 0.2 }
✅ handler: const result = await placeOrder(input)   ← 判断在领域层
```

handler 只做四件事：解析、**格式**校验（字段类型/必填，不是业务规则）、调用、
把结果和错误转成 HTTP 响应。

## 六、事务边界与并发

**一个用例一个事务，事务边界在应用层。** 领域层不知道事务存在。

**事务里不做慢的外部调用**（发邮件、调支付网关、发消息）。
外部服务卡 30 秒，你的数据库连接和锁就被占 30 秒。
正确做法：事务内只落一条"待发送"记录，事务外或后台任务里真发。

### 并发：找"读-判断-写"的形状

凡是"先读后写、写取决于读"的地方都有竞态：库存扣减、余额扣减、
唯一性检查、状态迁移、配额消耗。

```
❌ 读库存 → 应用层判断够不够 → 写新库存    （两个请求同时读到 2，都通过）
✅ 一条 SQL 条件更新：UPDATE ... SET stock = stock - 3 WHERE id = ? AND stock >= 3
   看影响行数，0 行就是库存不足
✅ 或 SELECT ... FOR UPDATE 锁行
✅ 最终防线：数据库 CHECK (stock >= 0)
```

**AI 默认写的是第一种。** 审计时直接搜这个形状（见最后一节）。

乐观锁（`version` 字段）适合"冲突少但要检测"的场景：
更新时带上读到的 version，影响 0 行说明有人先改了，让用户重试。

## 七、数据库

### schema

- **时间统一 UTC**，转换只在最外层做
- **金额用整数存最小单位**（分）或 decimal，**永远不要浮点**
- 每张表有 `created_at`、`updated_at`
- **不变量落成约束**：`NOT NULL`、`UNIQUE`、`CHECK`、外键。
  应用层校验会被绕过（另一个入口、一次脚本、AI 写的新接口），数据库约束不会
- 枚举用字符串不用数字（数字在日志里读不懂，加值时容易错位）

### 删除：先想清楚再写 DELETE

**删除是最容易做错且最难挽回的操作。** 动手前定：

| 问题 | 常见答案 |
|---|---|
| 软删除还是硬删除？ | 用户可见的业务数据基本都该软删（`deleted_at`） |
| 软删了怎么防止查出来？ | **在 repository 层统一过滤**，不要指望每个查询都记得加 |
| 唯一约束怎么办？ | 软删后名字要能复用的话，唯一索引要带 `deleted_at` 条件 |
| 保留多久、谁能真删？ | 写进 `docs/runbook.md` |
| 用户注销后关联数据怎么办？ | 匿名化还是级联删？合规上可能有要求 |

**AI 默认写硬删除。** 这是必审项。

### 查询

必看三件事：

1. **N+1**：循环里发查询。列表接口最容易中招
2. **无分页的列表接口**：现在 100 条没事，一年后 10 万条打满内存。
   **所有返回列表的接口一律强制分页**，包括"内部用的、数据不会多"的那个
3. **缺索引**：`WHERE`、`JOIN`、`ORDER BY` 用到的列。外键列不会自动有索引

### 迁移

见 `contract.md`。要点重复一遍：**每个迁移有 `down` 且实际验证过**，
破坏性变更三步走（加新 → 双写切读 → 删旧）。

## 八、错误处理

统一信封见 `contract.md`。代码侧：

- **区分预期错误和意外错误。** 预期的（库存不足、参数非法、无权限）是业务结果，
  返回 4xx 带错误码；意外的（数据库连不上、空指针）是 bug 或故障，
  记录完整堆栈 + traceId，返回 5xx 且**不要把内部信息泄露给客户端**
- **不要吞异常。** `catch {}` 和"catch 之后只打日志继续跑"是同一件事，
  都会让故障在几层之后以更难懂的方式爆出来
- **保留原始错误**，包装时带上 cause
- **重试要有退避和上限**，且只重试幂等操作。无脑重试会在下游抖动时把它打死

## 九、可观测性与审计日志

### 运行日志：给开发排查用

1. **结构化日志**（JSON），每条带 `traceId`，一个请求的所有日志能串起来
2. **traceId 在响应里返回**（错误信封里就有）。用户截图报错，你能直接搜
3. **健康检查**：区分 `/healthz`（进程活着，用于要不要重启）和
   `/readyz`（数据库等依赖可达，用于能不能接流量）——**两个的用途完全不同**
4. **关键路径埋点**：下单、支付、登录，成功/失败各记一条，带耗时

**日志里不许出现**：密码、token、cookie、完整卡号、身份证、完整手机号、
用户上传的原始内容。脱敏在写日志的地方做，不要指望后面过滤。

### 审计日志：给追责和合规用，和运行日志是两回事

| | 运行日志 | 审计日志 |
|---|---|---|
| 给谁看 | 开发排查 | 追责、合规、事故复盘 |
| 保留多久 | 几天到几周 | **明显更长** |
| 能不能丢 | 可以采样 | **不能丢** |
| 记什么 | 请求、耗时、错误 | **谁、在什么时候、对什么、做了什么、改成了什么** |

必须记审计的动作：

```
权限/角色变更 · 删除与恢复 · 数据导出 · 系统配置变更
登录（尤其失败）· 涉及钱的操作 · 管理员代用户操作
```

这类日志"平时没人看，出事时价值极高"——和备份一样。
**但审计日志同样不能记原始密钥和原始身份凭证。**

## 十、后台任务与定时器

- 任务要**幂等**——它一定会被重复执行（重试、重启、两个实例同时跑）
- 定时任务要**防重入**：一次跑得比间隔长时，不要叠起来
- **失败要能看见**：静默失败的定时任务是最难发现的故障
- 任务错误不要只打日志，要有失败计数或告警

长任务的正确形状：

```
HTTP 请求创建任务 → 立刻返回 job_id → 后台 worker 执行 → 前端轮询或推送进度
```

不要让 HTTP 请求一直等超长任务。

## 十一、后端审计速查

```bash
# 越权：查询没带归属过滤（最重要的一条）
grep -rnE "findById|SELECT .* WHERE id ?=" src/ | grep -viE "owner|user_id|tenant|workspace"

# "读-判断-写" 的竞态形状
grep -rn -A5 "SELECT.*stock\|SELECT.*balance\|SELECT.*quota" src/ | grep -i "UPDATE\|save"

# 硬删除
grep -rniE "DELETE FROM|\.delete\(|destroy\(" src/

# 吞掉的异常 / 硬编码地址 / 全字段查询
grep -rn "catch" src/ | grep -v "throw\|log\|return"
grep -rn "http://\|localhost\|127\.0\.0\.1" src/
grep -rn "SELECT \*" src/

# 日志泄密
grep -rniE "log.*\b(password|token|secret|cookie|id_?card|phone)\b" src/

# 自增 ID 泄漏到接口
grep -rnE "id: *(number|i32|i64|int)" src/ --include=*dto* --include=*response*
```

跑完这七条还剩下的，才值得人花时间逐行看。
