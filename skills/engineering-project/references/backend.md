# 技术专题：后端

与语言无关。讲的是**结构和决策**，不是某个框架的用法——框架用法查官方文档，
但下面这些东西查文档查不到，而且做错了要重写。

---

## 一、分层与依赖方向

```
接口层  handler / controller / route
   ↓    只做：解析请求、校验格式、调用用例、把结果和错误转成 HTTP
应用层  usecase / service
   ↓    只做：编排。开事务、按顺序调领域函数、发事件、处理跨上下文调用
领域层  domain
   ↑    业务规则。纯函数为主。**不 import 任何 IO**
基础设施 infra —— 数据库、外部 API、文件、消息队列、时钟、随机数
```

**唯一的硬约束：依赖方向朝内，领域层不依赖基础设施层。**

做到这一条的收益：

- 领域逻辑能用**纯单元测试**密集覆盖——不用起数据库，毫秒级，可以写几百条
- AI 在领域层的产出最容易验证（输入 → 输出，没有隐藏状态）
- 换数据库、换外部服务不影响业务规则

怎么做到：领域层需要外部数据时，**由调用方传进来**，不要自己去取。

```
❌ 领域函数内部 await db.query(...)
✅ 应用层先查好，把数据作为参数传给领域函数
```

**时钟和随机数也算 IO。** `now()` 和 `random()` 直接写在领域逻辑里，
那段逻辑就没法确定性测试。当参数传进去。这是 AI 特别容易忽略的一点。

## 二、handler 里不写业务判断

最常见的后端腐化方式：业务规则散在 handler 里，于是同一条规则在三个接口里
各写了一遍，其中两个是错的。

判据：**handler 里出现 `if` 判断业务条件，就该挪走。**

```
❌ handler 里：if (user.level === 'vip' && order.amount > 100) { discount = 0.2 }
✅ handler 里：const result = await placeOrder(input)  ← 判断在领域层
```

handler 该做的只有四件事：解析、格式校验（字段类型/必填，不是业务规则）、
调用、把结果和错误转成 HTTP 响应。

---

## 三、事务边界

规则：**一个用例一个事务，事务边界在应用层。**

- 领域层不知道事务存在
- 不要在领域函数里各自开事务——那样一个用例里会开五个事务，中间失败留下半个状态
- **事务里不做慢的外部调用**（发邮件、调支付网关、发消息）。
  外部服务卡 30 秒，你的数据库连接和锁就被占 30 秒。
  正确做法：事务内只落一条"待发送"记录，事务外或后台任务里真发。

### 并发

凡是"先读后写、写取决于读"的地方都有竞态。库存扣减、余额扣减、
唯一性检查、状态迁移，全部是。

```
❌ 读库存 → 应用层判断够不够 → 写新库存      （两个请求同时读到 2，都通过）
✅ 一条 SQL 里做条件更新：UPDATE ... SET stock = stock - 3 WHERE id = ? AND stock >= 3
   看影响行数，0 行就是库存不足
✅ 或者 SELECT ... FOR UPDATE 把行锁住
✅ 最终防线：数据库层 CHECK (stock >= 0)
```

**AI 默认写的是第一种。** 这是审计时必看的一项——
凡是涉及库存、余额、配额、唯一性的代码，直接搜有没有"读-判断-写"的形状。

## 四、数据库

### schema

- **时间统一 UTC**，字段名带时区意图（`created_at` 存 UTC）。
  时区转换只在最外层做。
- **金额用整数存最小单位**（分），永远不要用浮点。或者用 decimal。
- 每张表有 `created_at`、`updated_at`
- **不变量落成约束**：`NOT NULL`、`UNIQUE`、`CHECK`、外键。
  应用层校验会被绕过，数据库约束不会。
- 枚举值用字符串不用数字（数字在日志里读不懂，且加值时容易错位）

### 查询

必看的三件事（`audit.md` 的抽审项）：

1. **N+1**：循环里发查询。列表接口最容易中招。
2. **无分页的列表接口**：现在 100 条没事，一年后 10 万条把内存打满。
   **所有返回列表的接口一律强制分页**，包括"内部用的、数据不会多"的那个。
3. **缺索引**：`WHERE`、`JOIN`、`ORDER BY` 用到的列。
   外键列不会自动有索引（有些数据库）。

### 迁移

见 `contract.md`。要点重复一遍：**每个迁移有 `down` 且实际验证过**，
破坏性变更三步走（加新 → 双写切读 → 删旧）。

## 五、错误处理

统一信封见 `contract.md`。这里说代码侧：

- **区分预期错误和意外错误。** 预期错误（库存不足、参数非法、无权限）是业务
  结果，返回 4xx 带错误码；意外错误（数据库连不上、空指针）是 bug 或故障，
  记录完整堆栈 + traceId，返回 5xx 且**不要把内部信息泄露给客户端**。
- **不要吞异常。** `catch {}` 和"catch 之后只打个日志继续跑"是同一件事的两种
  写法，都会让故障在几层之后以更难懂的方式爆出来。
- **保留原始错误。** 包装时带上 cause，不要只留一句自己写的话。
- **重试要有退避和上限**，且只重试幂等操作。无脑重试会在下游抖动时把它打死。

## 六、可观测性最小集

不需要上一整套 APM。四样：

1. **结构化日志**（JSON），每条带 `traceId`。一个请求的所有日志能靠它串起来。
2. **traceId 在响应里返回**（错误信封里就有）。用户截图报错，你能直接搜。
3. **健康检查** `/healthz`：进程活着 + 数据库连得上 + 关键外部依赖可达。
   区分 liveness（要不要重启）和 readiness（能不能接流量）。
4. **关键路径埋点**：下单、支付、登录这些，成功/失败各记一条，
   带耗时。有了这个才能回答"是不是变慢了"。

**日志里不许出现**：密码、token、完整卡号、身份证、完整手机号、
用户上传的原始内容。脱敏在写日志的地方做，不要指望后面过滤。

---

## 七、后台任务与定时器

- 任务要**幂等**——它一定会被重复执行（重试、重启、两个实例同时跑）
- 定时任务要防重入：一次跑得比间隔长时，不要叠起来
- 失败要能看见：静默失败的定时任务是最难发现的故障
- 任务的错误不要只打日志，要有失败计数或告警

## 八、后端审计速查

审后端 PR 时，这五个搜索能筛掉大部分问题：

```bash
grep -rn "catch" src/ | grep -v "throw\|log\|return"   # 吞掉的异常
grep -rn "http://\|localhost\|127.0.0.1" src/          # 硬编码地址
grep -rn "SELECT \*" src/                              # 全字段查询
grep -rniE "password|token|secret" src/ | grep -i log  # 日志泄密
grep -rn "\.map\|for" src/ -A3 | grep -i "await.*query" # 循环里查询（N+1）
```
