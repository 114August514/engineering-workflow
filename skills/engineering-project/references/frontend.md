# 技术专题：前端

与框架无关。讲结构、一致性机制、验收——具体组件库用法查文档。

前端在 AI 协作里有一个特殊问题：**AI 看不见自己写的界面。**
它能写出编译通过、逻辑正确、但视觉上完全错位的页面。

所以这份文档的主线是：**把"看起来对不对"尽可能转化成"能不能被机器检查"。**

---

## 一、视觉一致性靠机制，不靠眼力

页面越改越乱，通常不是因为某个颜色难看，而是因为**每个页面各自决定用什么值**：
这里 `padding: 17px`，那里 `13px`；这个标题 `17px`，那个 `22px`。
单看每一处都没问题，合起来就是廉价感。

人可以靠眼力盯住这件事，AI 不行——它看不见。但它能做另一件事：
**只用允许的值。**

> **散值是机器可查的，视觉不协调不是。**
> Design tokens 把一个视觉问题，转化成了一个 lint 问题。

这是整套前端一致性方案的地基：**先把可选值收敛成有限集合，再禁止使用集合外的值。**
做到这一条，AI 写出来的页面即使没人看过，也不会跑偏太远。

---

## 二、Design tokens

把颜色、字号、间距、圆角、动效时长定义成变量，页面只引用变量。

```css
:root {
  /* 颜色：不要只定义"主色" */
  --color-bg: …;          --color-surface: …;      --color-elevated: …;
  --color-text: …;        --color-text-muted: …;   --color-text-disabled: …;
  --color-border: …;      --color-border-strong: …;
  --color-primary: …;     --color-primary-hover: …; --color-primary-active: …;
  --color-success: …;     --color-warning: …;      --color-danger: …;

  /* 间距：4px 或 8px 为基数，只留这几档 */
  --space-1: 4px;  --space-2: 8px;  --space-3: 12px;
  --space-4: 16px; --space-6: 24px; --space-8: 32px;

  /* 字号：5—6 档封顶 */
  --text-sm: 12px; --text-md: 14px; --text-lg: 16px;
  --text-xl: 20px; --text-2xl: 24px;

  /* 圆角、动效 */
  --radius-sm: 6px; --radius-md: 10px; --radius-lg: 16px;
  --duration-fast: 150ms; --duration-base: 200ms;
}
```

几条经验值：

| 维度 | 约束 | 越界的样子 |
|---|---|---|
| 字号 | **5—6 档封顶** | 出现 13px、15px、17px、22px |
| 间距 | 4px 的倍数，只留 6—8 档 | 7px、13px、19px、27px |
| 颜色 | 大面积中性色 + **一个**品牌色 | 每个功能一种新颜色 = 彩虹后台 |
| 阴影 | 默认不用，靠边框区分；只有浮层用 | 满屏卡片都带阴影 |
| 动效 | 150—200ms，缓动统一 | 这里弹跳、那里旋转、那里飞入 |

**这一条能被 CI 检查**（见第九节的速查命令）：搜代码里的裸值。
把它做成 lint 规则之后，"用了不该用的值"就永远不会进入人的评审视野——
这正是 `audit.md` 说的免审项该有的样子。

## 三、组件系统与交互状态

不要每个页面自己写 Button、Input、Modal。先封装一套，然后**页面只允许用这套**。

最小集合：`Button` `Input` `Textarea` `Select` `Checkbox` `Switch` `Modal`
`Drawer` `Tooltip` `Dropdown` `Tabs` `Card` `Badge` `Toast`
`EmptyState` `LoadingState` `ErrorState`。

最后三个最容易被漏，而它们恰恰是 AI 默认不写的（见第六节）。

### 每个可交互元素的状态必须完整

```
default · hover · active · focus · disabled · loading · selected · error
```

**状态缺失比颜色难看更致命**：一个 focus 态缺失的输入框，键盘用户直接不知道
自己在哪。而且状态混乱是"页面看起来不专业"最主要的来源——
不是颜色不好看，是同一个交互在不同页面表现不一样。

判据：**这个组件的每个状态，在 Style Guide 页面上都能看到吗？**（见第五节）

### 展示组件 / 容器组件

- **展示组件**：接收数据和回调，不取数据、不含业务判断。能脱离整个应用被单独渲染
- **容器组件**：取数据、组装、处理交互

好处和后端分层一样：展示组件可以用假数据直接测各种状态，
不需要 mock 掉半个应用。

拆分依据是**职责，不是行数**。一个组件同时管"取数据 + 布局 + 表单校验 + 提交"
就该拆，哪怕它只有 80 行。

## 四、页面级一致性

### 布局模板固定下来

```
AppShell
├── Sidebar / Nav
├── Topbar
├── Main Content
└── Toast Layer
```

常见页型定死结构，新页面照抄：

| 页型 | 结构 |
|---|---|
| 列表页 | 标题 + 操作按钮 + 筛选区 + 列表 + 分页 |
| 详情页 | 返回 + 标题区 + 信息区 + 操作区 |
| 设置页 | 左侧导航 + 右侧表单 |
| 空状态 | 图标 + 标题 + 说明 + **主操作按钮** |

不固定的话，每个新页面都会长得像另一个产品。

### 文案语气统一

UI 文案也是一致性的一部分，而且 AI 特别容易在这里飘。

```
❌ 混用：Save / 保存一下 / 确认保存 / 提交 / OK / 完成
✅ 统一：保存 · 取消 · 删除 · 导出 · 重试
```

错误文案要说**发生了什么 + 下一步做什么**：

```
❌ 出错了！ / Oops! / 系统异常啦～ / 请求失败，请稍后再试
✅ 保存失败，请检查网络后重试
✅ 该名称已存在，请换一个
✅ 文件超过 100MB，请压缩后再上传
```

把常用文案列进 Style Guide 页面，AI 就有地方对照。

## 五、Style Guide 页面：给 AI 的自查锚点

项目里放一个 `/design-system` 路由，把 tokens、每个组件的每个状态、
空/加载/错误三态、常用文案全部渲染出来。

**它比写一篇设计文档有用得多**，原因有三个：

1. **人**做新页面时直接对照，不用回忆
2. **AI** 可以读这个页面的源码，知道有哪些组件、每个组件有哪些 props 和状态——
   这比读散落在各处的用法可靠
3. **它是唯一能让"看不见界面"的 AI 自我核对的地方**：新组件加进来时，
   如果在这个页面上渲染不出全部状态，说明状态没写全

维护成本很低（它就是一个页面），但它是这套一致性方案里唯一一处
把"设计规范"变成"可运行代码"的地方。

---

## 六、三态是必须的，不是可选的

每一个从网络取数据的地方，**必须**处理四种情况：

| 状态 | AI 默认行为 | 常见后果 |
|---|---|---|
| 加载中 | ❌ 不写 | 无反馈，用户以为没点上，连点五次 |
| 成功但为空 | ❌ 不写 | 一片空白，看起来像坏了 |
| 成功有数据 | ✅ 只写这个 | — |
| 失败 | ❌ 不写 | 显示 `undefined` 或整页白屏 |

**空态要说明为什么空、下一步做什么**，不是留白。
**失败态要给下一步动作**（重试按钮），不是只显示"出错了"。

错误文案按 `contracts/errors.md` 的 `code` 分支，**不要匹配 message 字符串**——
message 是给人看的，随时会改。

## 七、契约消费：不等后端

契约定好之后前端立刻可以开工：

```
1. 从 contracts/ 生成类型 —— 不要手写一份，会漂移
2. 起 mock server（也从契约生成）
3. 对着 mock 开发完整功能，包括错误态
4. 后端就绪后切真接口 —— 两边对着同一份契约，这一步应该无事发生
```

**手写一份"和后端一样"的类型定义是最常见的漂移来源。** 生成，或共享同一个文件。

所有接口调用集中在 `api/` 一层，页面不直接 `fetch`：

```
api/client.ts   —— 统一处理 baseURL、鉴权头、错误信封解包、401 跳登录
api/orders.ts   —— 业务接口，返回类型明确
```

页面只调用 `listOrders()`。接口变了只改 `api/`，不用全项目找。

## 八、状态放在哪

按"这个状态属于谁"决定，不要一上来就上全局状态库：

| 状态类型 | 放哪 |
|---|---|
| 只有一个组件用 | 组件内部 |
| 几个相邻组件用 | 提到最近的共同父组件 |
| **服务端数据** | **数据获取库的缓存**，不是全局 store |
| 真正的全局（当前用户、主题） | 全局 store，尽量少 |
| **属于 URL 的**（页码、筛选、打开的详情 ID） | **URL 参数** |

两条最容易错的：

1. **服务端数据不要手动塞进全局 store。** 那样你要自己处理缓存失效、
   重新获取、并发请求、加载态——手写的版本一定有 bug
2. **能放 URL 的就放 URL。** 放进去就自动获得刷新不丢、可分享、前进后退可用；
   放组件 state 里这三样全没了

## 九、表单

前端 bug 密度最高的地方。四条：

1. **校验规则和后端一致，但后端那份不能省。** 前端校验是体验，后端校验是安全。
   AI 常常只写前端那份
2. **提交中禁用提交按钮**，否则双击会提交两次。后端也要幂等兜底（见 `backend.md`）
3. **错误显示在字段旁边**，不是顶部一个笼统提示
4. **失焦或提交时才校验**，不要每次按键都校验

## 十、AI 看不见界面：怎么验收

**能自动验的**（放进 `make check`）：

- 类型检查——接口字段改了，前端立刻编译失败
- 组件测试——断言"用户能看到什么、点了之后发生什么"，不断言内部实现
- 可访问性自动检查——缺 label、对比度不足、无 alt 大部分能查出来
- **token 裸值检查**（第九节命令）——这一条是把视觉问题变成 lint 的关键

**必须人看的**（G5 闸的一部分）：

- 真实浏览器里打开，**不是看 AI 的描述**
- 手机宽度看一次（默认 375px）
- 深色模式看一次
- 三态各看一次：断网、空数据、接口 500

**给 AI 反馈时要具体到像素和行为**：「提交按钮在 375px 下被截断了一半」，
不要说「移动端样式有问题」——后者它只能瞎猜。**截图是最有效的方式。**

---

## 十一、性能：只做三件事

不要提前优化。这三件普遍有效且便宜：

1. **列表虚拟化**——几百行以上才需要，但不做是卡死级别的问题
2. **图片**：指定宽高（防布局跳动）、懒加载、别传 4MB 原图
3. **首屏 JS 体积**——按路由分包

其余等有实测数据再说（见 `proportion.md`）。

---

## 十二、可访问性最低线

不只是道德要求，这几条同时决定了**能不能被自动测试**：

- 交互元素用**语义标签**（`button` 就是 `button`，不是能点的 `div`）
- 所有表单控件有关联的 label
- 键盘能走完主流程，焦点可见
- 正文对比度 ≥ 4.5:1
- 图片有 alt（纯装饰写空 alt）

**用语义标签的直接好处**：测试可以按"角色 + 名字"找元素
（"找那个叫『提交』的按钮"），这种测试不会因为改了 class 名就红。

## 十三、前端审计速查

```bash
# 绕过 token 的裸值 —— 这是视觉走样最主要的来源
grep -rnE '(padding|margin|gap|font-size|border-radius):\s*[0-9]+px' src/ --include=*.css --include=*.scss
grep -rnE '\[[0-9]+px\]|\[#[0-9a-fA-F]{3,8}\]' src/          # Tailwind 任意值
grep -rnE '#[0-9a-fA-F]{3,8}' src/ --include=*.tsx --include=*.vue  # 硬编码颜色

# 能点的 div —— 键盘用不了，测试也找不到
grep -rn "onClick\|@click" src/ | grep -E "<div|<span"

# 逃逸的类型 / 吞掉的错误
grep -rn ":\s*any\b\|as any\b" src/
grep -rn "catch" src/ | grep -v "set\|throw\|toast"

# 手写的接口类型（应该是生成或共享的）
grep -rn "interface.*Response\|type.*Response" src/ --include=*.ts | grep -v "api/generated"
```

再加一条人工的：**随便挑一个页面，把网络断掉 / 接口改成返回空数组 /
接口改成返回 500，看三次表现。**
