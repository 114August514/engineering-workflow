# 技术专题：前端

与框架无关。讲结构、状态、验收——具体组件库的用法查文档。

前端在 AI 协作里有一个特殊问题：**AI 看不见自己写的界面。**
它能写出编译通过、逻辑正确、但视觉上完全错位的页面。所以前端的验收方式
和后端不一样——见第六节。

---

## 一、契约消费：不等后端

`contract.md` 定好契约之后，前端立刻可以开工：

```
1. 从 contracts/ 生成类型 —— 不要手写一份，会漂移
2. 起 mock server（也从契约生成）
3. 对着 mock 开发完整功能，包括错误态
4. 后端就绪后切真接口 —— 两边对着同一份契约，这一步应该无事发生
```

**手写一份"和后端一样"的类型定义是最常见的漂移来源。** 生成，或者共享同一个
文件。

---

## 二、三态是必须的，不是可选的

每一个从网络取数据的地方，**必须**处理四种状态：

| 状态 | 常见错误 |
|---|---|
| 加载中 | 没有任何反馈，用户以为点击没生效，于是连点五次 |
| 成功但为空 | 显示一片空白，看起来像坏了。**空态要说明为什么空、下一步做什么** |
| 成功有数据 | ✅ AI 只会写这个 |
| 失败 | 显示"undefined"或整页白屏 |

**AI 默认只实现第三种。** 这是前端审计的第一条：随便挑一个页面，
把网络断掉、把接口改成返回空数组、把接口改成返回 500，看三次表现。

失败态要给用户**下一步动作**（重试按钮），不要只显示一句"出错了"。
错误文案按 `contracts/errors.md` 的 `code` 分支，**不要匹配 message 字符串**。

---

## 三、状态放在哪

按"这个状态属于谁"决定，不要一上来就上全局状态库：

| 状态类型 | 放哪 | 例 |
|---|---|---|
| 只有一个组件用 | 组件内部 | 下拉框开没开 |
| 几个相邻组件用 | 提到最近的共同父组件 | 表单各字段 |
| 服务端数据 | **数据获取库的缓存**，不是全局 store | 订单列表、用户信息 |
| 真正的全局 | 全局 store（尽量少） | 当前登录用户、主题 |
| 属于 URL 的 | **URL 参数** | 当前页码、筛选条件、打开的详情 ID |

两条最容易错的：

1. **服务端数据不要手动塞进全局 store。** 那样你要自己处理缓存失效、
   重新获取、并发请求、加载态——这些是数据获取库的工作。
   手写的版本一定会有 bug。
2. **能放 URL 的就放 URL。** 筛选条件、页码、打开的弹窗，放 URL 里就自动获得
   刷新不丢、可分享、前进后退可用。放组件 state 里这三样全没了。

---

## 四、组件边界

和后端的分层是同一个思路：

- **展示组件**：接收数据和回调，不取数据、不含业务判断。可以脱离整个应用被单独渲染。
- **容器组件**：取数据、组装、处理交互。

好处同样是可测：展示组件可以用假数据直接测各种状态，
而不需要 mock 掉半个应用。

组件文件变长时的拆分依据：**按职责拆，不按行数拆**。
一个组件同时管"取数据 + 布局 + 表单校验 + 提交"就该拆，
哪怕它只有 80 行。

---

## 五、表单

表单是前端 bug 密度最高的地方。四条：

1. **校验规则和后端一致**——但**后端的校验不能省**。前端校验是体验，
   后端校验是安全。AI 常常只写前端那份。
2. **提交中禁用提交按钮**，否则用户双击会提交两次。后端也要幂等兜底。
3. **错误显示在字段旁边**，不是顶部一个笼统的提示。
4. **不要在每次按键时校验**——失焦或提交时校验，否则用户刚输一个字符就看到
   一片红。

---

## 六、AI 看不见界面：怎么验收

这是前端最关键的一条。

**能自动验的**（放进 `make check`）：

- 类型检查——接口字段改了，前端立刻编译失败
- 组件测试——渲染 + 断言"用户能看到什么、点了之后发生什么"，
  不要断言内部实现
- 可访问性自动检查——大部分工具能查出缺 label、对比度不足、无 alt

**必须人看的**（G5 闸的一部分）：

- 真实浏览器里打开，**不是看 AI 的描述**
- 手机宽度看一次（默认 375px）
- 深色模式看一次（如果支持）
- 三态各看一次：断网、空数据、接口 500

**给 AI 反馈时要具体到像素和行为**："提交按钮在 375px 宽度下被截断了一半"，
不要说"移动端样式有问题"——后者它只能瞎猜。截图给它是最有效的方式。

---

## 七、性能：只做三件事

不要提前优化。这三件是普遍有效且便宜的：

1. **列表虚拟化**——超过几百行的列表才需要，但不做的话是卡死级别的问题
2. **图片**：指定宽高（防布局跳动）、懒加载、别传 4MB 原图
3. **首屏 JS 体积**——按路由分包。这个不做，慢是全局性的

其余的等有实测数据再说。

---

## 八、可访问性最低线

不是道德要求，是这几条同时也决定了"能不能被自动测试"：

- 交互元素用**语义标签**（`button` 就是 `button`，不是能点的 `div`）——
  div 点不了键盘，也没法被测试工具找到
- 所有表单控件有关联的 label
- 键盘能走完主流程（Tab 顺序合理，焦点可见）
- 正文对比度 ≥ 4.5:1
- 图片有 alt（纯装饰的写空 alt）

**用语义标签的直接好处**：测试可以按"角色 + 名字"找元素
（"找那个叫『提交』的按钮"），这种测试不会因为改了 class 名就红。

---

## 九、前端审计速查

```bash
grep -rn "onClick" src/ | grep "<div"        # 能点的 div
grep -rn "any" src/ --include=*.ts*          # 逃逸的类型
grep -rn "catch" src/ | grep -v "set\|throw" # 吞掉的错误
grep -rLn "isLoading\|isPending" src/**/*page*  # 可能没处理加载态的页面
```

再加一句：**看有没有手写的接口类型定义**（应该是生成或共享的）。
