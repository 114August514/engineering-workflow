# 缺陷修复

**产物不是"修好的代码"，是一条先红后绿的回归测试 + 一个写下来的根因。**

只有代码改动的 bug 修复会复发——因为没有任何东西阻止它再次发生。

---

## 一、为什么 bug 修复不能走 T0

一行的修改**看起来**像微改。这是分流表里最常见的误判：

> 「就改一个 `>` 为 `>=`，跑一下 `make check` 通过了，提交。」

问题：`make check` 通过说明**现有测试**没被破坏，不说明这个 bug 被修好了——
既然它是 bug，就说明现有测试根本没覆盖它。没有新增测试的修复，
等于把这个 bug 从"已知"变成"已知且没人防着"。

**规则：凡是修 bug，哪怕只改一个字符，都走这条流程。**

---

## 二、七步

```
1. 复现       —— 写一条能稳定复现的测试，跑，看它红
2. 定位根因   —— 问"为什么"，直到答案指向一个具体的错误假设
3. 修         —— 最小改动
4. 变绿       —— 那条测试从红变绿，其余测试保持绿
5. 找同类     —— 同一个错误假设在别处还成立吗
6. 回填       —— 这个 bug 说明 spec / 不变量缺了一条吗
7. 评审       —— 按下面第四节的缺陷评审清单
```

### 第 1 步：复现不了就不要修

没有一条会失败的测试，你就没有办法知道自己修没修好——只能靠"我试了一下好像好了"。

复现测试要**尽可能小**：不是端到端点一遍，是直接调用出问题的那个函数。
小的复现测试同时也是最好的定位工具。

如果复现不了（偶发、只在生产出现、依赖特定数据），**先解决复现问题**：
加日志、拿生产数据脱敏后构造用例、缩小范围。在没复现的情况下改代码，
是在猜。

### 第 2 步：根因不是症状

一直问"为什么"，直到答案是一个**具体的错误假设**：

> 现象：库存扣成了负数
> 为什么？→ 两个请求同时通过了库存检查
> 为什么？→ 检查和扣减不在一个原子操作里
> 为什么？→ 写的时候**假设了**"读到的库存在写之前不会变"
> ← 根因：这个假设。它在别的地方可能也成立

**判据：根因应该能解释"为什么当初会写成这样"。**
如果你的结论是"这里少写了一个 if"，那还没到根因。

### 第 3 步：修根因，不是症状

判据是**改动在哪一层**：

| 改动位置 | 通常意味着 |
|---|---|
| 在调用点加一个防御性判断 | ⚠️ 多半是症状——根因还在，下一个调用点还会中招 |
| 在领域逻辑里改判断条件 | 可能是根因 |
| 改数据模型 / 加数据库约束 | 通常是根因 |
| 在最外层 catch 住然后忽略 | ❌ 这是把 bug 藏起来，不是修 |

### 第 5 步：找同类——AI 最容易跳过，也是收益最高的

根因是一个**错误假设**，那个假设很可能在别处也被用了。

```bash
# 例：根因是"读-判断-写"没有原子性，那就搜所有同样形状的地方
grep -rn "stock\|balance\|quota" src/ -A5 | grep -B3 "UPDATE\|save"
```

找到的同类：要么一起修（如果便宜），要么**登记成任务**（如果贵）。
不许假装没看见。

### 第 6 步：回填到 spec 和不变量

大部分 bug 是需求里缺了一条：

- 这个情况 spec 里根本没写 → 补一条验收标准（带新的 `REQ-ID`）
- 这是一条本该始终成立的规则 → 补一条 `INV-*` 到 `docs/glossary.md`，
  **并且落成数据库约束**
- 这是状态机里一条没列出的迁移 → 补进状态机表

**这一步是 bug 修复和普通改动最大的区别**：普通改动实现 spec，
bug 修复经常反过来**修正 spec**。

## 三、提交与命名

```
fix: 库存并发扣减为负

根因：检查和扣减不是原子操作，隐含假设了读到的库存在写之前不变。
改为条件更新 + 数据库 CHECK 约束兜底。
同类问题：账户余额扣减有同样形状，已登记 TASK-042。

REQ-ORD-007  INV-002
```

回归测试的名字里带上新的 `REQ-ID` 或 `INV-ID`，这样 `make audit`
的双向追溯能覆盖到它。

## 四、缺陷评审清单

比切片评审短，10 分钟，但有五条是硬的：

- [ ] **有没有一条先红后绿的回归测试？** 没有 = 阻塞，不用往下看了
- [ ] 把修复**撤掉**，那条测试会红吗？（真验一次，别推理）
- [ ] **根因写下来了吗**，还是只说了"修好了"
- [ ] **同类问题找过了吗**？找的方法说得出来吗（贴出那条 grep）
- [ ] 这是不是该变成一条不变量 / 验收标准？补了吗
- [ ] 修的是根因还是症状（看改动在哪一层）
- [ ] 有没有顺手改别的（`git diff --stat` 对照）

---

## 五、AI 修 bug 的典型失败

| 失败模式 | 长什么样 | 怎么发现 |
|---|---|---|
| **改症状** | 在调用点加了个 `if (x == null) return` | 问"根因是什么"，答不上来就是症状 |
| **没有回归测试** | 只改了实现，说"我验证过了" | 看 diff 里有没有新测试 |
| **放宽断言让它过** | 改了已有测试的断言 | `git diff` 里看测试文件的删除行 |
| **只修一个实例** | 三处同样的问题只修了报上来的那处 | 问"同类找过吗"，要它贴搜索命令 |
| **顺手重构** | 修复混在一堆无关改动里 | `git diff --stat` |
| **吞掉异常当作修复** | `try { ... } catch {}` | grep 空 catch |
| **改测试而不是改代码** | 让测试适应错误的行为 | 看被改的是测试还是实现 |

## 六、什么时候 bug 修复要升级成 T2

这几种情况说明不是一个 bug，是设计问题，走完整流程：

- 修它需要改契约或数据库 schema
- 根因是一条**领域不变量从一开始就没定**
- 同类问题超过三处（说明是系统性的，该改结构而不是逐个打补丁）
- 修完之后你说不清"为什么这样就对了"

这时候回 P1/P2：补不变量、写 ADR，再按结构性改动来做。
