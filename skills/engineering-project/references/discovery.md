# P-1 需求调研

**目标**：判断这东西**该不该做**、该做成什么样。
**产物**：几条有证据支撑的判断 + 一个决定（做 / 不做 / 换个做法）
**闸门**：G0——做不做

P0 是把**已知的意图**说精确（EARS、例子、非目标）。
这一步在它前面：**你怎么知道要做的是对的东西？**

**这是全流程唯一一个"决定不做"是成功结果的阶段。** 砍掉一个项目，
比之后任何一个决策都省钱。

---

## 一、先判断要不要做这一步

**跳过它是常态，不是例外。** 满足任一条就直接进 P0：

- 自用工具、脚本、内部小工具
- 需求方已经拍板，你的任务是实现不是论证
- 问题你自己天天遇到（你就是用户，证据在你身上）
- **做一个最小版本的成本 < 认真调研的成本**（见第五节）

需要做的信号：

- 要投入超过两周
- 你在替**别人**解决问题，而且你不是那个"别人"
- 有多个明显不同的方案，选错了要重写
- 已经有类似的东西存在，但你不确定为什么它不够

判断不了就问一句。**这一步的开销必须和项目体量匹配**，一个两天的工具做三天调研是荒唐的。

---

## 二、调研什么：五个问题

按"答案会不会改变决定"排序。不改变决定的不查。

| # | 问题 | 答不上来的后果 |
|---|---|---|
| 1 | **这个问题真实存在吗？谁有？** | 做出来没人用 |
| 2 | **他们现在怎么解决的？** | 你的方案可能还不如现状 |
| 3 | **为什么现有方案不够？** | 直接买/用现成的就完了 |
| 4 | **不做会怎样？** | 说不出来就是不值得做 |
| 5 | **技术上做得到吗？最不确定的一环是什么？** | 做到一半发现根本不行 |

第 2 问是最容易被跳过、也最有信息量的一问。**"手工做"也是一种现有方案**——
而且经常是够用的那个。

---

## 三、怎么调研

### 问过去的行为，不问未来的意愿

这一条比其他所有技巧加起来都重要。

> ❌「你需要一个自动导出功能吗？」→ 人会礼貌地说需要
> ✅「你上次导数据是什么时候？当时具体怎么做的？花了多久？后来那份数据用来干嘛了？」

**未来的意愿不是证据，过去的行为才是。** 人对假想功能的回答几乎没有预测力，
但对上周做过什么的回答是事实。

配套的几个好问题：

- 「这事你多久遇到一次？」——频率决定值不值得
- 「上次遇到的时候，你为此花了多少时间／钱？」——痛的量化
- 「你为了绕过它，做过什么奇怪的事吗？」——**自制的变通方案是最强的需求信号**
- 「如果这个问题永远不解决，会怎样？」——逼出真实影响

### 先找现成的产品

这是 `reuse.md` 在产品层的版本：**不要重复造产品**。

按顺序找：现成的 SaaS / 开源项目 / 你已经在付费的工具里有没有这个功能 /
两个现有工具拼一下能不能解决。

**"买/用现成的"经常是正确答案**，尤其当这件事不是你的核心竞争力时。
认真评估过再决定自己造，理由写进 ADR。

### 看已经存在的数据

比访谈便宜、也比访谈诚实：现有日志、工单/客服记录、搜索关键词、
现有功能的使用数据、别人在 issue 里抱怨过什么。

### 最小验证：有时候做出来就是最好的调研

如果一个能用的最小版本两天就能做出来，**别调研两周**。
直接做，然后看有没有人用。

这和 P3 的 walking skeleton 是同一个思路，只是用来验证需求而不是验证技术。

---

## 四、AI 在这一步最危险

**AI 会非常流畅地生成一份看起来很专业的调研报告，里面的数据全是编的。**

市场规模、竞品的用户量、"研究表明 73% 的用户……"——这类句子读起来极其可信，
而且正好是人最难核实的部分。它比写错代码危险得多：代码错了测试会红，
调研错了整个项目建在沙上。

硬规则：

1. **每一条事实性陈述必须附来源**（链接、文档、访谈记录、日志查询）
2. **没有来源的一律标成「未验证的推测」**，不许混在事实里
3. **不许生成具体数字**（百分比、市场规模、用户量），除非能指出出处
4. 人只需要核一件事：**这条判断的证据是什么？** 答不上来就划掉

反过来，AI 在这一步真正有用的地方：整理访谈记录找模式、列出现有方案清单
让人去核、把模糊的说法追问成具体例子、指出你没考虑到的失败场景。

---

## 五、调研的成本上限

按 `proportion.md` 的标准卡住自己：

> **调研的成本不应该超过做一个最小版本的成本。**

超了就直接做。做出来是最强的调研——它同时验证了需求、可行性和你的估算能力。

另一条：**如果调研从来没让你砍掉过什么，那你不是在调研，是在找支持自己想法的证据。**
最有价值的调研结论通常是这三个之一：

- 不做
- 做一个**小得多**的东西
- 问题不在这儿，在别处

## 六、产物：不是报告，是判断

**不要写调研报告。** 写几条判断，每条带证据，最后给一个决定。

```markdown
# <项目名> 调研

## 判断

1. **这个问题真实存在** —— 运营三个人都在手工导表，其中两个自己写了
   Excel 宏来绕过（自制变通方案 = 强需求信号）
   证据：2026-07-20 与 A/B/C 的访谈记录（链接）

2. **现状是手工，每周约 2 小时/人** —— 不是"很痛"，但一年就是 300 小时
   证据：访谈时让他们回忆了上周的实际操作

3. **现成方案不适用** —— 我们的订单结构是自定义的，评估过的三个导出工具
   都要求标准 schema
   证据：<三个工具的文档链接>

4. **未验证的推测**：他们可能还想要定时导出。只有 A 提过一次，没有其他人
   印证，暂不作为依据。

## 决定

做，但只做手动触发的固定列导出（约三天）。定时导出列入非目标。

## 最不确定的一环

10 万条以上的导出会不会超时 —— 放进 P3 骨架里验证。
```

一页以内。写不下说明还没想清楚。

## 七、G0 闸：人决定做不做

人看三样，十五分钟：

- [ ] 每条判断**指得出证据**（推测的有没有被明确标出来）
- [ ] 「不做会怎样」这一问答上来了
- [ ] 调研有没有让范围**变小**过（一次都没有 → 多半是在找支持性证据）

决定「做」之后进 P0，把它变成 EARS 验收标准；决定「不做」就到此为止，
**把这份判断留在仓库里**——半年后有人再提同一个想法时，它能省下重来一遍的时间。

## 八、反模式

| 现象 | 为什么是问题 |
|---|---|
| 问"你需要 X 吗" | 人会说需要。问过去的行为 |
| AI 生成带具体数字的市场分析 | 数字多半是编的，而且最难核实 |
| 调研两周做两天的东西 | 直接做出来更快也更准 |
| 调研结论永远是"做" | 在找支持性证据，不是在调研 |
| 写了二十页报告没有结论 | 产物是判断和决定，不是报告 |
| 跳过第 2 问（现在怎么解决） | 手工方案经常够用，你可能在解决不存在的问题 |
| 给自用小工具做正式调研 | 你就是用户，证据在你身上 |
