# P4 契约先行

**目标**：把人机接缝、前后端接缝、模块接缝都固化成可校验的契约。
**产物**：`contracts/` 目录 + `migrations/`
**闸门**：G4——人审 schema diff

**为什么单独设一个阶段**：契约是整个项目里**最小、最致命、最可读**的东西。
一个 200 行的 OpenAPI 文件决定了几千行实现代码长什么样。人花二十分钟审它，
比花四小时审实现代码的收益高一个数量级。

而且契约定死之后，**前端 agent 和后端 agent 可以并行工作而不互相阻塞**——
这是 AI 协作里最大的一次并行度提升。

---

## 一、契约包括什么

| 契约 | 放哪 | 谁消费 |
|---|---|---|
| HTTP 接口 | `contracts/openapi.yaml` | 前端、外部调用方、mock server |
| 共享类型 | `contracts/types.*`（或从 schema 生成） | 前后端 |
| 错误码表 | `contracts/errors.md` | 前端、运维、客服 |
| 数据库结构 | `migrations/` | 后端、DBA、数据分析 |
| 事件/消息格式 | `contracts/events.*` | 生产者、消费者 |
| 配置项 | `.env.example` | 运维、部署 |

**能生成的就不要手写两遍**：从 OpenAPI 生成前后端类型、生成 mock server、
生成契约测试。手写两遍必然漂移。

---

## 二、三条硬规则

### 1. 契约变更单独提交

契约的 diff 混在几百行实现里，人就审不动了——而这恰恰是最该被审的部分。

```
提交 A：契约变更（几十行，人认真审）  ← G4 闸在这
提交 B：后端实现（按契约来）
提交 C：前端实现（按契约来）
```

`audit.sh` 会检测同一个 commit 里既有 `contracts/` 又有大量实现代码的情况，
并标为"必须拆分"。

### 2. 破坏性变更必须有迁移路径

破坏性 = 会让现有调用方挂掉。删字段、改字段类型、改字段含义、
把可选变必填、改错误码语义，都算。

处理方式（三步走，别一步到位）：

```
第一步：加新的，旧的保留，标 deprecated
第二步：所有调用方切到新的（有几个调用方就有几次改动）
第三步：删旧的
```

三步之间可以隔几天。**数据库迁移尤其不能一步到位**——
先加列（可空）→ 双写 → 回填 → 切读 → 停写旧列 → 删列。
中间任何一步失败，系统都还能正常跑。

### 3. 迁移必须可回滚

每个迁移文件都要有 `down`。写完当场验一次：

```bash
make migrate && make migrate-down && make migrate
```

**没验证过的回滚脚本等于没有。** AI 写的 `down` 经常是错的——
它会写"删掉这一列"，但忘了数据已经没了。所以破坏性迁移的 `down`
如果做不到无损，要在文件里显式写明"此迁移不可无损回滚，回滚方案见 runbook"。

## 三、错误模型：统一信封

先定死，之后所有接口照办。定得晚了，前端要处理五种错误格式。

```json
{
  "error": {
    "code": "OUT_OF_STOCK",
    "message": "库存仅剩 2 件",
    "details": { "sku": "A-001", "available": 2 },
    "traceId": "01J8X..."
  }
}
```

约定：

- `code` 是**稳定的机器可读串**，前端按它做分支。定下就不改，
  全部集中登记在 `contracts/errors.md`。
- `message` 给人看，可以改、可以翻译。**前端不许按 message 做逻辑判断。**
- `details` 结构由 `code` 决定，在错误码表里写清楚。
- `traceId` 必须能在日志里搜到。用户截图报错，运维靠这个定位。
- HTTP 状态码只表达大类（4xx 你错了 / 5xx 我错了），细节靠 `code`。

错误码表：

```markdown
| code | HTTP | 含义 | details 字段 | 前端建议行为 |
|---|---|---|---|---|
| `OUT_OF_STOCK` | 409 | 库存不足 | `sku`, `available` | 提示并把数量调到可用值 |
| `PAYMENT_TIMEOUT` | 504 | 支付网关超时 | `orderId` | 提示"处理中"，轮询订单状态 |
```

**AI 特别容易在这里出错**：它会随手 `throw new Error("库存不足")`，
前端只能字符串匹配。审 PR 时专门看这一条。

## 四、契约先行怎么让前后端并行

```
1. 人审通过 contracts/openapi.yaml           ← G4
2. 从契约生成：前端类型 + mock server + 后端类型 + 契约测试
3. ┌─ 后端 agent：实现真接口，跑契约测试
   └─ 前端 agent：连 mock server 开发，不等后端
4. 后端就绪后前端切真接口 —— 因为两边都对着同一份契约，这一步应该无事发生
```

**契约测试**是关键：它验证真实接口的响应符合契约（字段、类型、必填、
错误码）。有它才敢让前端信 mock。没有它，第 4 步就会变成一周的联调。

---

## 五、什么时候不需要这么正式

单人项目、前后端同一个人、同一个仓库、类型能直接共享——
可以把 OpenAPI 换成**一份共享的类型定义文件**，前后端都 import 它，
编译器就是契约检查器。规则不变（单独提交、破坏性变更三步走、错误码集中登记），
只是载体轻了。

**不能省的是错误码表和迁移**，这两个跟项目规模无关。

---

## 六、出口检查（G4 闸）

人审这几样，应该二十分钟内看完：

- [ ] 每个接口的**错误路径**都定义了，不是只定义了成功响应
- [ ] 每个字段：必填还是可选、格式约束、单位（金额是分还是元？时间是 UTC 吗？）
- [ ] 分页、排序、过滤的约定统一（不要一个接口 `page` 一个 `offset`）
- [ ] 时间统一 UTC + ISO 8601，金额统一最小单位整数
- [ ] 破坏性变更有三步迁移方案
- [ ] 迁移的 `down` **实际执行验证过**
- [ ] 错误码全部登记在表里，没有临时字符串
- [ ] 契约变更是独立提交
