# 作业日志：在途、回退、并发

借操作系统的三个机制解决三个真问题：

| OS 机制 | 对应的真问题 |
|---|---|
| **预写日志（WAL）** | AI 会话会死（被压缩、被打断、超时）。死在半路时仓库处于未知状态，下一个会话不知道刚才在干什么 |
| **undo log** | `git revert` 撤不掉已经跑过的迁移、已经发出去的部署、已经建好的外部资源 |
| **锁与粒度** | 多个 agent / 多个人并行时改同一块地方 |

---

## 零、先说不做什么

**git 已经是代码的日志了。** 这份东西只补 git 记不了的三样：
动手前的**意图**、**仓外副作用**、**在途状态**。

明确不做（否则就是 `proportion.md` 说的过度设计）：

- ❌ 任务数据库 / 结构化存储 —— markdown 就够，人能读、git 能 diff
- ❌ 真锁（flock / 锁服务）—— 跨机器无效，且多一类故障模式
- ❌ 调度器 —— 谁先做哪个是人的判断
- ❌ 把 diff 抄进日志 —— 那是 git 的活

已经有 issue tracker 的团队，**用你们的 issue tracker**，
这份日志只补它记不了的「仓外副作用」和「在途状态」两栏。

---

## 一、日志条目就是任务卡

不新增产物。`slices.md` 的任务卡加三个字段，放进 `docs/journal/`，就是日志条目。

**一个条目一个文件**（`docs/journal/2026-07-26-2140-order-stock.md`），
不是一个大文件追加——并行的 agent 各写各的文件，**永远不会有合并冲突**。
这是 maildir 的做法，也是避免共享可变状态的一般原则。

```markdown
# REQ-ORD-003 库存不足时拒绝下单

- 状态：进行中          ← 进行中 / 已完成 / 已放弃 / 已回退
- 认领：agent-A（或人名）
- 上下文：src/order/     ← 锁的粒度，见第三节
- 开始：2026-07-26 21:40

## 意图
在 order 上下文实现库存不足时拒绝下单，扣减要原子。

## 预期改动
- src/order/domain/stock.ts
- src/order/app/place-order.ts
- tests/order/stock.test.ts

## 仓外副作用          ← 最重要的一节，见第二节
无。

## 回退方式
git revert <commit>

## 验收
make check；测试名含 REQ-ORD-003

## 禁区
不动 src/payment/、不动 migrations/、不加依赖
```

**预写：先写这个文件，再动手。** 顺序不能反。

理由就是 WAL 的理由：崩溃在"写完意图、还没做完"是可恢复的——
下一个会话读到这个文件就知道该做什么、该检查什么。
反过来（先做后记）崩溃就什么都没留下。

写这个文件的成本是一分钟。它换回来的是会话死掉时不用重新推理。

## 二、仓外副作用：undo log 真正不可替代的地方

`git revert` 能撤销代码，**撤不掉**：

| 副作用 | 撤销方式 |
|---|---|
| 在真实库上跑过的迁移 | `make migrate-down`（**前提是验证过**，见 `contract.md`） |
| 已部署的版本 | runbook 里的回滚命令 + 耗时 |
| 建好的外部资源（bucket、DNS、webhook 注册、第三方应用） | 逐个写清楚怎么删 |
| 轮换过的密钥 | 旧的已作废，只能再轮换一次 |
| **已发出的邮件 / 消息 / 通知** | **不可撤销** —— 必须标明 |
| 写进第三方系统的数据 | 看对方提供什么接口 |

### 硬规则

> **产生仓外副作用之前，先在日志里写下怎么撤销它。**

**写不出撤销方式的操作，本身就是一个需要人点头的信号。**
这条比它看起来更有用——它把"这一步能不能反悔"从一个事后才想起的问题，
变成一个动手前必须回答的问题。

和 `proportion.md` 的主线是同一条：**按可逆性决定投入**。
这里是它的操作化版本。

## 三、并发：锁的粒度是限界上下文

多个 agent 并行时会撞车。粒度选择：

| 粒度 | 问题 |
|---|---|
| 文件级 | 太细。一条切片会碰七八个文件，锁不过来 |
| 仓库级 | 太粗。等于串行，并行就没意义了 |
| **限界上下文** | ✓ 正好 |

`src/order/` 一个 agent，`src/payment/` 另一个，互不干扰。

**这是 P1 划边界在多 agent 场景下的第二个价值**——
第一个是收窄单个 agent 需要读的上下文（`handoff.md`），
第二个就是它天然是并行的单位。上下文划得好，并行就不打架。

### 怎么"上锁"

不需要真锁。**日志里状态为「进行中」的条目就是锁**：

```bash
make journal        # 看当前有哪些进行中，各自占着哪个上下文
```

开工前扫一眼，要动的上下文已经被占着 → 换一个，或者等，或者去问。

### 跨上下文的改动要串行

碰 `contracts/`、`migrations/`、`AGENTS.md`、根目录配置的改动，
**影响所有上下文**，必须独占——这类改动本来就是 T2 档，本来就要过闸门。
不要和别的并行工作叠在一起。

## 四、孤儿锁：会话死了怎么办

OS 里进程持锁崩溃会留下孤儿锁，需要超时回收。AI 会话完全一样，
而且**发生频率高得多**。

`journal.sh` 报出**超过 24 小时还是「进行中」**的条目。对每个孤儿：

```
1. git status / git log —— 工作区里有没有半成品？有没有提交？
2. 读日志条目的「预期改动」，对照实际改了什么
3. 三选一：
   - 接着做（把认领人改成自己）
   - 回滚重来（按「回退方式」执行，状态改「已回退」）
   - 就这样了（状态改「已放弃」，说明为什么，未做的部分回到 spec）
```

**不许直接删掉孤儿条目。** 它记录了当时的意图，而且可能有仓外副作用还挂着——
那才是真正危险的东西（见下节）。

## 五、崩溃恢复：新会话的开场动作

一个 AI 会话接手时，前三十秒固定做这三件事：

```bash
make journal          # 有没有进行中的条目？是我的吗？
git status            # 工作区干净吗？有没有半成品
git log --oneline -5  # 最近提交做到哪了
```

三者对不上就先对齐，**不要在状态不明时开始写新代码**——
那是在一个未知的基线上叠改动，最后谁也说不清哪些是谁的。

`journal.sh` 会特别标出**状态不是「已完成」但有仓外副作用**的条目：
这些是最危险的——可能有一次迁移跑了一半、一个部署发出去了没人管、
一个外部资源建了没登记。

## 六、什么时候值得记，什么时候不值得

用 `proportion.md` 的标准卡一遍，别让它变成仪式：

| 情况 | 记不记 |
|---|---|
| T0 微改（文案、常量、格式） | **不记**。git 就够了 |
| T1 功能切片 | **记**。这是主要场景 |
| TF 缺陷修复 | **记**，因为根因和"找同类"的结论值得留下 |
| T2 结构性改动 | **记**，而且要写清楚仓外副作用 |
| 任何有仓外副作用的操作 | **必记**，无论多小 |
| 多个 agent / 多人同时在做事 | **必记**，这时它是锁 |
| 单人、单会话、十分钟做完 | 不记也行 |

**判据：如果这件事做到一半我掉线了，别人（或下一个我）需要知道什么？**
答案是"什么都不需要"，就不用记。

## 七、完成之后

- 状态改「已完成」，补一句实际改了什么（如果和「预期改动」不一致，
  说明为什么——这一条经常暴露出范围膨胀）
- 仓外副作用**实际发生了的**，登记进 `docs/runbook.md`——
  日志是临时的，runbook 是长期的
- 结论、踩到的坑、被否掉的方案，按 `handoff.md` 的规则落盘到
  `docs/decisions/` 或 runbook

**已完成的条目保留**，不要删。它是这个仓库的操作史，
里程碑复盘（`review.md` 第六节）时翻一遍很有用——
能看出这段时间实际在做什么，和 spec 说的是不是一回事。
