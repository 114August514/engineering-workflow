# 存量项目接入

前面七个阶段假定的是 0→1。但**大部分实际工作发生在已经存在的代码上**，
而 SDD 类流程公认的短板就是难以 retrofit。

这份讲怎么把这套东西接到一个已经在跑的项目上，**不推倒重来**。

---

## 一条铁律

> **不要为了接入这套流程去做大重构。**

新流程从**下一条切片**开始生效，老代码原地不动。

理由：一次性重构是这类接入最常见的死法——它产生一个巨大的、无法评审的 diff，
风险全部堆在同一天，而且在你还不了解这份代码的时候就动它。
这恰好违反了这套流程自己的每一条（PR 尺寸上限、按可逆性投入、垂直切片）。

老代码的改造靠**碰到就顺手改一点**：这次切片碰到哪个文件，
就把那个文件的命名对齐术语表、把那段逻辑的测试补上。不碰的不动。

---

## 接入顺序：从最便宜的开始

每一步都能独立产生价值，随时可以停在任意一步。

### 第 1 步：包一层标准动词（半小时）

**不改现有工具链**，只是在外面套一层转发：

```makefile
# stack.mk —— 转发到项目已有的命令，一个字都不用改现有配置
SETUP     := pnpm install --frozen-lockfile
DEV       := pnpm dev
FMT       := pnpm lint:fix
FMT_CHECK := pnpm lint
LINT      := pnpm lint && pnpm depcheck
TYPECHECK := pnpm tsc --noEmit
TEST      := pnpm test
BUILD     := pnpm build
```

收益立刻就有：人和 AI 从此只需要记 `make check`，
`AGENTS.md` 里写的验证命令不会因为将来换工具而失效。

**这一步不产生任何风险**，因为它没改任何现有行为。

### 第 2 步：体检，但不要一次修完（一小时）

```bash
~/.claude/skills/engineering-project/scripts/doctor.sh
```

它会报一堆红。**不要一次性修完**——挑两条：

1. **`.env` 有没有进过仓库**（`git log --all -- .env`）。有就当作已泄露，
   立刻轮换密钥。这条不可逆，优先级最高
2. **CI 有没有跑 `make check`**。没有就先接上，让第 1 步的成果被守住

其余的红项记成任务，按"碰到再修"推进。

### 第 3 步：术语表反向提取（一到两小时）

不要从零设计，**从现有代码里捞**：

```bash
# 数据库表名和核心类型名，通常就是这个系统的名词
ls migrations/ | sed 's/[0-9_]*//;s/\.sql//' | sort -u
grep -rhoE '(class|interface|type|struct) [A-Z][A-Za-z]+' src/ | awk '{print $2}' | sort | uniq -c | sort -rn | head -30
```

人扫一遍，挑出**真正的领域概念**（不是 `Utils`、`Manager`、`Helper`），
填进 `docs/glossary.md`，重点填**「不是什么」那一列**。

这一步经常会直接暴露问题：同一个概念有两个名字、一个名字指两个东西。
**先记下来，不要立刻改名**——改名是重构，走第一条铁律。

### 第 4 步：spec 只补正在改的部分（持续）

**绝对不要一上来全量补 spec。** 给一个跑了两年的系统补几百条 REQ，
结果是一份没人读、也没人维护的文档。

做法：**这次切片改什么，就给什么补 REQ**。

- 追溯率从 0 开始慢慢长，这是正常的
- `make audit` 只对"这次改动"生效，不会因为历史代码没有 REQ 就报一片红
- 半年后回头看，被改动过的部分自然都有了 REQ；从没被碰过的部分，
  说明它也不需要

### 第 5 步：契约从现有接口生成（视情况）

不要重新设计接口。从现有代码生成 OpenAPI / 类型定义，
放进 `contracts/`，**然后冻结它**——从此改接口必须先改契约。

存量项目的接口通常不一致（这个用 `page` 那个用 `offset`，
错误格式有三种）。**不要一次统一**：把现状如实记下来，
新接口按统一约定写，旧接口碰到再说。

`contracts/errors.md` 可以先只登记**新增**的错误码。

## 已有测试很烂怎么办

常见情况：覆盖率数字很好看，但测试是 mock 自证的，或者早就被 skip 了。

不要全部重写。三条：

1. **先把 skip 的测试列出来**（`make review` 会报）。逐条决定：
   修好、还是删掉。**留着 skip 的测试是最坏的选项**——它假装存在
2. **新代码按新标准**：测试先行、先看红、带 REQ-ID
3. **碰到的老代码补测试**：改哪个函数，就先给那个函数补一条能失败的测试，
   再改。这同时也是修 bug 的流程

**不要给老代码补覆盖率。** 补出来的多半是同义反复的测试，
消耗评审精力却什么都不保证。

## 什么时候不值得接入

按 `proportion.md` 的标准诚实判断：

- **马上要废弃/重写的系统** —— 别浪费
- **纯脚本、一次性工具** —— `make check` 都嫌重
- **别人的仓库，你只是偶尔提 PR** —— 跟他们的约定走

判据：**这个项目还会被持续改多久？** 三个月以内的，只做第 1、2 步就够。

---

## 常见的接入翻车

| 错误 | 后果 |
|---|---|
| 一上来大重构，"先把结构理顺" | 巨大 diff、风险集中、在最不了解代码时动它 |
| 全量补 spec | 几百条没人读的 REQ，两周后就过期 |
| 把 `doctor.sh` 的红项一次修完 | 一个混杂了十件事的 PR，人审不动 |
| 立刻按术语表全局改名 | 纯机械改动淹没真实改动，且必然漏改 |
| 强行统一所有历史接口 | 破坏性变更，调用方全炸 |
| 给老代码补覆盖率 | 假测试，消耗评审精力 |

共同点：**都是想一次性把存量问题清干净。**
这套流程的整个设计前提是"小步、可评审、可回退"，
接入它的过程本身也必须遵守这一条。

---

## 出口检查

接入到什么程度算成功？**不看覆盖率，看这四条**：

- [ ] `make check` 能跑，且 CI 在跑它
- [ ] `.env` 确认没进过仓库历史
- [ ] `AGENTS.md` + `docs/conventions.md` 就位，新会话读它就知道怎么干活
- [ ] **最近三条切片**都有 REQ-ID、都有先红后绿的测试

第四条是关键：它衡量的是**新工作**是否在流程内，
而不是历史包袱清干净了没有。历史包袱永远清不完。
