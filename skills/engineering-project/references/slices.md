# P5 垂直切片实现

**目标**：一次交付一条用户可见的完整路径。
**产物**：一个小 PR
**闸门**：G5——按 `audit.md` 的分级清单审

这是唯一的高频闸门，所以这一阶段全部设计围绕一件事：**让人审得动**。

---

## 一、什么叫垂直切片

一条切片必须同时满足：

- **用户可见**——不是"加个 service 层"，是"用户能创建订单了"
- **端到端**——从界面/接口一路到数据库，穿过所有层
- **能独立上线**——合并进去就能用，不依赖还没做的东西

反例（这些是水平切片，不要这么切）：

| 错误切法 | 为什么错 |
|---|---|
| "先把所有数据模型建好" | 建完了不能用，也不知道建对没有 |
| "先写完所有 API，再写前端" | 到联调才发现契约不对，返工 |
| "先搭一个通用的 CRUD 基类" | 在只有一个用例时抽象，抽象一定是错的 |

切片顺序按 `spec.md` 的验收标准来，一次一条 REQ 或一小组紧密相关的 REQ。

---

## 二、任务卡

每条切片开工前写一张，写在 PR 描述或 `docs/tasks/` 里。
**这是人机对接的标准接口**，格式固定：

```markdown
## 背景
<一两句，为什么现在做这个。指向 REQ-ID>

## 目标
实现 REQ-ORD-003：库存不足时拒绝下单

## 验收标准
- 商品 A 库存 2，提交数量 3 → 返回 409 OUT_OF_STOCK，
  消息含"库存仅剩 2"，订单不落库
- 商品 A 库存 2，提交数量 2 → 成功，库存变 0
- 并发两个数量 2 的请求 → 只有一个成功

## 约束
- 用 contracts/openapi.yaml 里已定义的 POST /orders，不要改契约
- 库存扣减必须在同一事务里，参考 docs/decisions/0001-choose-postgres.md

## 验证
make check
并且新测试的名字里包含 REQ-ORD-003

## 禁区
- 不要动 src/payment/
- 不要动 migrations/（这次不需要新表）
- 不要引入新依赖
```

**"禁区"这一节不能省。** AI 在实现时遇到不顺手的地方，会倾向于"顺手改一下
旁边那个"。写明禁区，一是它会遵守，二是审的时候 `git diff --stat`
一眼就能看出它有没有越界。

## 三、内环：七步，先搜后写

```
0. 先搜          —— 这个仓库里已经有了吗？标准库有吗？已装的依赖有吗？
1. 写测试        —— 按验收标准写，测试名里带 REQ-ID
2. 跑，看它红    —— 必须亲眼看到失败，且失败原因是对的
3. 最小实现      —— 只让这条测试变绿，不多写
4. 跑，看它绿
5. 清理          —— 重复的抽掉、命名对齐术语表；测试保持绿
6. make check + 提交
```

**第 0 步是新加的，而且经常是省时间最多的一步。** AI 最常见的重复造轮子
不是引错了库，是**在这个仓库里已经有一个实现的情况下又写一个**——
它不会主动全局搜。动手前 grep 一下功能关键词，十秒钟的事。
安全、时间与时区、协议解析、金额精度这些**一律用成熟实现**，见 `reuse.md`。

**第 2 步不能跳。** 没见过失败的测试有可能什么都没断言、有可能测的根本不是这段
代码。AI 写完实现再补测试时，几乎必然写出"刚好能过"的测试。这是 AI 代码里
最常见也最难发现的问题：**测试看起来很多，实际上什么都没保证**。

第 3 步的"最小"是认真的。不要顺手加"以后可能要用的参数"、不要提前抽象、
不要为想象中的故障写防御。**AI 写额外代码几乎零成本，但人审它的成本是一样的**——
每一行没必要的代码都在消耗那个最稀缺的资源。判据和识别信号见 `proportion.md`。

---

## 四、测试策略：AI 场景下的取舍

| 层 | 数量 | 测什么 | 为什么 |
|---|---|---|---|
| 领域单元测试 | **多**（几十上百条） | 业务规则、不变量、状态机非法迁移、边界值 | 快、稳、不需要环境。领域层是纯的，所以能这样测 |
| 集成测试 | **少**（每个接缝几条） | 真数据库、真事务、真外部调用（沙箱） | 慢但真。只测接缝，不重复测业务规则 |
| 端到端 | **极少**（关键路径几条） | 用户能不能走完主流程 | 最慢最脆，只保住命脉 |

### 必须专门写的四类测试

AI 天然会写第一类，后三类要盯着它写：

1. 正常路径 ✅ 它会写
2. **不变量违反**——尝试违反 `glossary.md` 里每条 INV，断言被拒绝
3. **非法状态迁移**——状态机表里没列出的组合，逐个断言被拒绝
4. **异常路径**——spec 里每条"如果……那么……"

### 禁止的测试写法

| 反模式 | 长什么样 | 为什么是假的 |
|---|---|---|
| mock 自证 | mock 掉被测函数依赖的一切，然后断言 mock 被调用了 | 只验证了"代码调用了它自己写的调用"，重构必挂，行为错了却过 |
| 同义反复 | `assert(add(1,2) === add(1,2))` | 恒真 |
| 无断言 | 只调用不断言，"不抛异常就算过" | 返回了错的值也过 |
| 快照兜底 | 一切都存快照，出错就 update snapshot | 快照更新变成条件反射，等于没测 |
| 测实现细节 | 断言内部调用了哪个私有方法 | 一重构就红，人会开始忽略红灯 |

**如果覆盖率上去了但你不敢改代码，说明测试是假的。**

## 五、PR 尺寸上限

**默认 400 行 diff，一条切片一个 PR。**

理由就是开头那组数据：AI 让 PR 体积涨了 154%，评审时间涨了 91%。
超过某个体积，人的评审就从"逐行看"退化成"扫一眼点同意"——
这时候闸门形同虚设，还不如没有。

超了怎么办：

- 先拆出**纯机械改动**（重命名、移动文件、格式化）单独一个 PR，
  这种 PR 人可以三十秒扫完
- 契约/迁移单独一个 PR（本来就该这样）
- 还超，说明切片切大了，回去重切

生成的代码（schema 生成的类型、锁文件）不计入行数，但要在 PR 里说明
"这部分是生成的"。

## 六、AI 汇报格式

每完成一条切片，按这个格式说，不要只说"做完了"：

```
做了什么：实现 REQ-ORD-003，新增 src/order/domain/stock.ts 和 3 条测试
没做什么：并发场景只测了两个请求，没做压测（风险表里那条留到 P6）
怎么验证的：make check 全绿，粘贴输出；手动跑了库存边界 0/1/2 三种情况
不确定的：库存扣减用了 SELECT FOR UPDATE，但没验证过高并发下的锁等待时间
故意没处理的：支付网关返回未知状态码——没见过，且真发生会走人工对账，
              不值得现在写分支。已记进风险表
碰了什么：只动了 src/order/，没进禁区
```

**最后三节最有价值**，它们直接告诉人该重点审哪里：

- **"不确定的"**——我在哪里可能错了
- **"故意没处理的"**——我在哪里**主动决定不做**，以及理由。
  没有这一节，人无法区分"漏了"和"想过后决定不做"（见 `proportion.md`）
- **"没做什么"**——简化的、降级的、留给下次的

AI 说"全部完成、没有问题、没有不确定的"时，通常意味着它没在找问题。

## 七、出口检查（G5 闸）

- [ ] `make check` 全绿，**输出贴出来了**
- [ ] 每条验收标准都有对应测试，测试名里有 REQ-ID
- [ ] 有测不变量违反和非法状态迁移的测试
- [ ] `git diff --stat` 里没有禁区文件
- [ ] diff 行数在上限内
- [ ] 没有偷偷新增依赖
- [ ] 按 `audit.md` 的分级清单过一遍

审的时候用 `make audit` 生成待审清单，它会自动标出必审项。

**请求评审的格式、反馈怎么给、收到反馈怎么处理**——见 `review.md`。
其中一条值得在这里重复：汇报里那句"我最不确定的三个地方"是强制的，
它让评审者直接去最可能有问题的地方，比从零扫一遍整个 diff 便宜一个数量级。

一组切片做完之后，别忘了**里程碑复盘**（`make review` + `review.md` 第六节）——
每个 PR 都过了不代表整体还立得住。
