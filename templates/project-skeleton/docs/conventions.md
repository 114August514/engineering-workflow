# 本项目的工作约定

`AGENTS.md` 是宪法——短、只放禁令和指针。**细节在这里。**
这份文件随项目走，不依赖任何人装了什么 skill。

---

## 动手前

按这个顺序找一遍，**第一层命中就不用往下问**：

1. **这个仓库里已经有了吗** —— `grep -rn "关键词" src/`。
   最常见的重复造轮子不是引错库，是仓库里已经有一个了又写一个
2. 标准库 / 运行时里有吗
3. 已经装了的依赖里有吗（先看依赖清单）
4. 才轮到新增依赖 —— 而且要先说明理由

**这些一律用成熟实现，不许手搓**：密码哈希与加密、token 签发校验、随机数、
时区与日期换算、HTTP/JSON/CSV/URL 解析、金额精度、重试与退避、限流、
数据库驱动与迁移工具。

判据：**这个东西的边界情况我能列全吗？** 列不全就别自己写。
（CSV 看起来是"按逗号分割"，直到你遇到引号里的逗号、引号里的换行、BOM、CRLF。）

抄进来的代码必须**适配**：命名换成 `docs/glossary.md` 里的词、删掉用不到的部分、
错误走统一信封、日志走本项目格式、放进正确的目录。
**看不懂的代码不要抄进来**——出问题时你没法调。

判据：抄进来的东西读起来应该像这个项目里长出来的，而不是贴上去的。

## 做多少

按**可逆性**决定投入：

- 不可逆或很贵的（数据、钱、契约、权限、迁移、密钥）—— 防住
- 可逆的、能重试的 —— **让它失败**，但保证失败可见（异常往上抛 + 日志 + traceId）

没预期到的情况，**大声失败好过悄悄兜底**。`catch` 住返回默认值，
是把一个十分钟能定位的崩溃，变成三个月后才发现的数据污染。

要加一层抽象 / 一个配置项 / 一段防御之前，先回答三句：
**哪条 REQ 要求了这个？这个情况实际发生过吗？删掉它会怎样？** 答不上来就别加。

过度设计的可查信号：只有一个实现的接口、没人用非默认值的配置项、
只有一个策略的策略模式、没测过慢就上的缓存、为"将来可能换"包的适配层。

**三次法则**：同样的东西出现第三次再抽象，第二次先老实复制。

纯推理出来的风险 —— **写进风险记录，不写进代码**。

## 写测试

顺序固定：

```
0. 先搜（上面那四层）
1. 写测试 —— 按验收标准写，名字里带 REQ-ID
2. 跑，看它红 —— 必须亲眼看到失败，且失败原因是对的
3. 最小实现 —— 只让这条测试变绿，不多写
4. 跑，看它绿
5. 清理 —— 命名对齐术语表，测试保持绿
6. make check + 提交
```

**第 2 步不能跳。** 没见过失败的测试可能什么都没断言。写完实现再补测试时，
几乎必然写出"刚好能过"的测试——这是最常见也最难发现的问题：
**测试看起来很多，实际什么都没保证。**

必须专门写的三类（正常路径不用提醒也会写）：

- **不变量违反**：尝试违反 `docs/glossary.md` 里每条 `INV-*`，断言被拒绝
- **非法状态迁移**：状态机表里没列出的组合，逐个断言被拒绝
- **异常路径**：spec 里每条「如果……那么……」

禁止的写法：mock 掉一切然后断言 mock 被调用了、只调用不断言、
一切都存快照、断言内部调用了哪个私有方法。

**如果覆盖率上去了但你不敢改代码，说明测试是假的。**

## 需求变了怎么办

- 加需求 → 新 ID 往后排；**ID 号不复用**
- 改需求 → **ID 不变，改内容，立刻改测试**（先让它红），不许拖到"下次一起改"
- 砍需求 → 从 spec 删掉，同时删掉或改写它的测试

**ID 相同挡不住内容变了**：需求从「拒绝」改成「转预售」，测试仍断言 409
且照样通过。`make audit` 会检查"REQ 定义变了但引用它的测试没跟着变"并挡住合并。

## 修 bug

改一行也不算微改。产物不是"修好的代码"，是**一条先红后绿的回归测试 + 写下来的根因**。

```
1. 先复现 —— 写一条会失败的测试，跑，看它红。复现不了就先解决复现，不要猜着改
2. 定位根因 —— 一直问"为什么"，直到答案是一个具体的错误假设
3. 最小改动修掉，测试变绿
4. 找同类 —— 同一个错误假设在别处还成立吗？贴出你搜索的命令
5. 回填 —— 这暴露了 spec 缺一条验收标准、或缺一条不变量吗？补上
```

判据：**根因应该能解释"为什么当初会写成这样"。** 结论是"这里少写了一个 if"
就还没到根因。在调用点加防御性判断，通常是在修症状。

## 开工与收工

**开工前**（新会话前三十秒，固定动作）：

```bash
make journal            # 有没有在途的？是我的吗？要动的上下文被占着吗
git status              # 工作区干净吗
git log --oneline -5    # 做到哪了
```

三者对不上就先对齐，**不要在状态不明时开始写新代码**。

**动手前**先在 `docs/journal/` 写一条意图（`./scripts/journal.sh --new <slug> <上下文>`），
填完再动手——顺序不能反。会话会死（压缩、打断、超时），
写完意图那一刻是可恢复的，反过来什么都不剩。

**产生仓外副作用之前**（跑迁移、部署、建外部资源、发消息），
先在日志里写下**怎么撤销它**。`git revert` 撤不掉这些。
**写不出撤销方式 = 需要人点头**，先停下来问。

**长任务定期提交**，不要攒到最后——提交就是检查点，
崩在中间时能回到最近一个绿的状态。

**收工时**状态改已完成/已放弃，实际发生的仓外副作用登记进 `docs/runbook.md`。

## 收到评审反馈

1. **先复述理解，再动手** —— 修错东西的成本远高于多问一句
2. **不许表演性同意。**「你说得对，我马上改」然后改掉症状，是最坏的情况。
   反馈也可能是错的——有具体依据（指向某行代码、某份文档、某条测试）就说出来
3. **一次只修反馈，不夹带**别的改动
4. 每条阻塞项回应清楚：改了什么、**加了哪条测试证明它修好了**

## 汇报

完成时说清六件事：

1. 做了什么
2. **没做什么**（简化的、降级的、留给下次的）
3. 怎么验证的（贴 `make check` 输出）
4. **哪里不确定**（写满三条；说"没有不确定的"通常意味着没在找问题）
5. **故意没处理的**（想过、决定不做、以及理由）
6. 碰了哪些文件（`git diff --stat`）

不要用"应该没问题""看起来是对的"收尾。要么验证过并给出证据，要么明说没验证。
