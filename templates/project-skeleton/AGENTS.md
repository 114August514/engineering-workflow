## 验证

提交前必须跑：

```bash
make check
```

它包含格式检查、lint、类型检查、测试。**不要另外发明命令**，
不要直接调用底层工具——`make check` 是唯一的真理。

声称"做完了"之前，跑它，并把输出贴出来。

## 目录

- `src/<上下文>/` —— 按限界上下文分，**不按技术层分**
- `src/*/domain/` —— 纯业务规则，**不许 import 任何 IO**（数据库、HTTP、文件、时钟、随机数）
- `src/*/app/` —— 用例编排，事务边界在这一层
- `src/*/infra/` —— 数据库、外部调用
- `contracts/`、`migrations/` —— 🔴 改动前必须先问人
- `docs/spec.md` 验收标准 · `docs/glossary.md` 术语与不变量 · `docs/decisions/` 为什么这么设计

## 命名

所有概念用 `docs/glossary.md` 里的名字。代码标识符、数据库列、接口字段、
日志字段全用同一个词。需要新概念时**先往术语表加一行**再写代码。

## 不变量

不能违反 `docs/glossary.md` 里的 `INV-*` 条目。数据库约束是最后一道防线，
不要因为应用层已经校验过就省掉它。

## 禁止

- 不许改 `contracts/`、`migrations/`、认证授权相关代码 —— 先提出来让人决定
- 不许新增依赖 —— 先说明为什么，以及自己写 50 行能不能替代
- 不许 skip / 注释掉 / 放宽失败的测试。测试红了就是代码错了
- 不许在错误里用临时字符串，错误码登记在 `contracts/errors.md`
- 不许硬编码配置（URL、密钥、路径），从环境变量读
- 不许写只调用不断言的测试，或者 mock 掉一切然后断言 mock 被调用了
- **不许过度设计**：只有一个实现就不要抽接口，没人用的配置项就是常量，
  同样的东西出现第三次再抽象（第二次先老实复制）
- **不许为想象中的故障写防御**。没发生过、也不是同类系统已知模式的风险，
  写进风险表，不写进代码。没预期到的情况**让它失败**——
  大声失败好过悄悄兜底，`catch` 住返回默认值是把 bug 埋起来

## 动手前先搜

写任何一段有名字的功能之前，按这个顺序找一遍：

1. **这个仓库里已经有了吗** —— `grep -rn "关键词" src/`。
   最常见的重复造轮子不是引错库，是仓库里已经有一个了又写一个
2. 标准库 / 运行时里有吗
3. 已经装了的依赖里有吗（先看依赖清单）
4. 才轮到新增依赖 —— 而且要先说明理由

**这些一律用成熟实现，不许手搓**：密码哈希与加密、token 签发校验、随机数、
时区与日期换算、HTTP/JSON/CSV/URL 解析、金额精度、重试与退避、限流、
数据库驱动与迁移工具。判据是「这个东西的边界情况我能列全吗」——列不全就别自己写。

抄来的代码必须**适配**：命名换成术语表里的词、删掉用不到的部分、
错误走统一信封、日志走本项目格式、放进正确的目录。
**看不懂的代码不要抄进来。**

## 做多少

按**可逆性**决定投入：

- 不可逆或很贵的（数据、钱、契约、权限、迁移、密钥）—— 防住
- 可逆的、能重试的 —— 让它失败，但**保证失败可见**（异常往上抛 + 日志 + traceId）

要加一层抽象/一个配置项/一段防御之前，先回答：**哪条 REQ 要求了这个？
这个情况实际发生过吗？删掉它会怎样？** 答不上来就别加。

## 写测试

先写测试，**跑一次看它红**，再写实现。测试名里带上对应的 `REQ-ID`。
每条正常路径至少配一条异常路径。

## 修 bug

改一行也不算微改。顺序是固定的：

1. **先写一条会失败的回归测试**，跑，看它红。复现不了就先解决复现，不要猜着改
2. 定位**根因**——一直问"为什么"，直到答案是一个具体的错误假设
3. 最小改动修掉，测试变绿
4. **找同类**——同一个错误假设在别处还成立吗？贴出你搜索的命令
5. 根因写进提交信息；如果这暴露了 spec 缺一条验收标准或缺一条不变量，补上

**没有回归测试的修复不算修完。** 在调用点加一个防御性判断，通常是在修症状。

## 收到评审反馈

1. **先复述理解，再动手** —— 修错东西的成本远高于多问一句
2. **不许表演性同意。** "你说得对，我马上改"然后改掉症状，是最坏的情况。
   反馈也可能是错的——如果你有具体依据（指向某行代码、某份文档、某条测试），
   说出来，别默认顺从
3. **一次只修反馈，不夹带**别的改动，否则二次评审要重新分辨哪些是你自己加的
4. 每条阻塞项回应清楚：改了什么、**加了哪条测试证明它修好了**

## 汇报

完成时说清六件事，不要只说"做完了"：

1. 做了什么
2. **没做什么**（简化的、降级的、留给下次的）
3. 怎么验证的（贴 `make check` 输出）
4. **哪里不确定**
5. **故意没处理的**（想过、决定不做、以及理由）—— 没有这一节，
   人分不清"漏了"和"想过后决定不做"
6. 碰了哪些文件（`git diff --stat`）

不要用"应该没问题"、"看起来是对的"收尾。要么验证过并给出证据，
要么明说没验证。
